Cade Mini

Cade Mini is a standalone coding agent. It keeps one rule at the center of the design:

The session log is the source of truth. The model-visible history is a deterministic projection. Request construction only produces the current request.

The result is a small agent that can survive compaction, window changes, and process restarts without inventing history.

Quickstart

Cade Mini requires Python 3.12 or newer. The repository uses uv for development and for the cade-mini entry point.

Install and authenticate

From the repository root:

uv sync --locked

Cade Mini owns its credential store at ~/.cade-mini/auth.json. Log in with Sign in with ChatGPT (SIWC) in a browser:

uv run --locked cade-mini login

The browser flow registers Cade Mini on first use and reuses that registration on later sign-ins. It stores a stable host ID at ~/.cade-mini/host.json. SIWC has no device-code flow. On a headless host, complete the login locally, copy auth.json, and let the remote host create its own host ID on the next login. Or use an API key.

For an OpenAI API key, use a hidden key prompt or set the environment variable:

uv run --locked cade-mini login --provider openai
export OPENAI_API_KEY=...
uv run --locked cade-mini --provider openai --model gpt-5.5 "Review this project."

The default provider is chatgpt. Set provider and model in cade-mini.json to choose other startup defaults. Cade Mini supports only the OpenAI Responses protocol: chatgpt for ChatGPT plan usage and openai for an API key. Mini does not read Cade's credentials, skills, or settings.

Run one task

uv run --locked cade-mini "Read README.md and explain the entry point in three bullets."

The same command can be written explicitly:

uv run --locked cade-mini exec "Read README.md and explain the entry point."

Cade Mini runs in the current directory by default. Use --project-root to point at another workspace.

Choose a mode

  • act is the default. Reads run directly; writes and shell commands ask.
  • build allows structured writes and read-only shell commands. Mutating shell commands still ask.
  • plan hides write and edit tools and denies mutations. Read-only shell commands are allowed.
uv run --locked cade-mini --mode plan "Propose a fix for the failing test."
uv run --locked cade-mini --mode build "Fix the bug and run the test."

For non-interactive automation, --yes approves asks, and --read-only denies writes and shell commands. Prefer rule-based allows over --yes for shared repositories; see Configuration.

Continue work

Sessions live under .cade-mini/sessions by default.

uv run --locked cade-mini --list-sessions
uv run --locked cade-mini --continue "What did you change?"
uv run --locked cade-mini --resume SESSION_ID "Continue the task."

Omitting the task starts the interactive REPL. See CLI for all REPL commands.

Build the docs

uv sync --locked --extra docs
uv run --locked python -m cade_mini.docs check
uv run --locked python -m cade_mini.docs build

Open docs/index.html. The docs source is under docs/.

CLI

The cade-mini entry point runs one task, starts a REPL, or manages sessions.

cade-mini [TASK] [options]
cade-mini exec TASK [options]

exec is an explicit alias for a one-shot task. Without a task, cade-mini starts the interactive REPL.

Login

cade-mini login
cade-mini login --provider openai

--provider defaults to chatgpt, which uses Sign in with ChatGPT (SIWC) in a browser. openai uses api_key with a hidden input prompt. Credentials are stored in ~/.cade-mini/auth.json; the stable SIWC host ID is stored in ~/.cade-mini/host.json. Login does not change project provider or model settings. Cade Mini supports only the OpenAI Responses protocol.

One-shot options

  • --project-root PATH sets the workspace. The default is the current directory.
  • --config PATH selects a config file. The default is <project-root>/cade-mini.json.
  • --provider NAME, --model NAME, and --effort EFFORT override provider defaults.
  • --mode plan|build|ask selects the work mode. Default is build.
  • --sandbox read-only|workspace-write|danger-full-access selects filesystem scope. Default is workspace-write; Windows skips OS confinement.
  • --network / --no-network controls sandbox networking. Default is enabled.
  • --read-only / --no-read-only controls mutation denial. Read-only shell commands remain available.
  • --yes approves asks. Use it only in trusted, non-interactive contexts.
  • --auto-review / --no-auto-review lets the model review ask-level calls.
  • --max-steps N bounds model steps.
  • --context-window N overrides the model context window.
  • --json emits JSONL events for a one-shot task.
  • --steer TEXT injects guidance at the next model step; repeatable.
  • --queue TEXT queues a REPL task to run after the current task; repeatable.

Sessions

  • --list-sessions prints ID, update time, and title, then exits.
  • --continue resumes the latest session in the project.
  • --resume resumes the latest session; --resume ID resumes a specific one.
  • --sessions-dir PATH changes the session directory. A relative path is resolved against the project root.
  • --undo restores the latest file snapshot and exits without contacting a provider.

--continue and --resume cannot be combined.

Goals

  • --goal TEXT sets the workspace goal before running.

REPL commands

  • /new starts a new session.
  • /resume [ID] resumes the latest or a specific session.
  • /sessions lists project sessions.
  • /fork [N|ENTRY] forks before a recent user turn or entry. N=1 is the latest.
  • /clone copies the current branch to a new session.
  • /tree shows entries; * marks the active branch.
  • /rewind [N] creates a session without the latest N user turns.
  • /compact summarizes older turns.
  • /new-context [NOTE] starts a new window, optionally with a handoff note.
  • /mode [MODE] shows or switches the execution mode.
  • /permissions [clear] shows or clears session grants.
  • /undo [N] restores the latest N snapshots.
  • /goal [TEXT|done|clear] shows, sets, completes, or clears the goal.
  • /context prints the session ID, provider, budget, and event count.
  • /steer TEXT queues guidance for the next model step.
  • /queue TEXT queues a task to run after the current one.
  • /stop cancels the current task at the next safe point.
  • /help prints the command list.
  • /exit or /quit exits.

REPL input

  • @path attaches a workspace file to the task.
  • $skill loads a skill body into the task.
  • !command runs a shell command without contacting the model. Permission checks still apply.
Review @src/cade_mini/core/loop.py and use $review-only
!git status

During a task, the REPL keeps reading input:

  • /steer TEXT appends guidance at the next model step.
  • /queue TEXT runs TEXT after the current task.
  • /stop cancels at the next safe point.
  • Other text is queued as a follow-up task.

Steering is applied between steps, not inside a provider stream or a running tool. See Steering and queueing.

Exit codes

  • 0: the run completed.
  • 1: the run ended without completion, or no snapshot was available for --undo.
  • 2: argument, configuration, or startup error.
  • 130: login was cancelled.

Configuration

Cade Mini reads <project-root>/cade-mini.json by default. Use --config PATH to select another file. Command-line options override the file; the file overrides built-in defaults.

The file is strict: unknown keys and invalid values are rejected instead of silently ignored.

Example

{
  "provider": "chatgpt",
  "model": "gpt-5.6-luna",
  "reasoning_effort": "high",
  "context_window": 128000,
  "max_steps": 30,
  "sessions_dir": ".cade-mini/sessions",
  "mode": "build",
  "sandbox": "workspace-write",
  "network": true,
  "read_only": false,
  "instructions": true,
  "note": true,
  "memory": true,
  "auto_review": false,
  "prompt_modules": ["identity", "tool_discipline", "working_note", "environment"],
  "rules": [
    {
      "tool": "bash",
      "command_prefix": "git status",
      "decision": "allow"
    }
  ]
}

Fields

  • provider, model: provider name and model identifier. Use chatgpt for ChatGPT plan usage (Sign in with ChatGPT) or openai for an OpenAI API key. The CLI flags override both.
  • reasoning_effort: provider reasoning effort. The CLI flag is --effort.
  • context_window: model context window in tokens.
  • max_steps: maximum model steps in one run.
  • sessions_dir: session directory. Relative paths resolve against the project root.
  • mode: plan, build, or ask. Default is build; replace old act values with ask.
  • sandbox: read-only, workspace-write (default), or danger-full-access. Windows skips OS confinement regardless of this setting.
  • network: allow tool network access. Default is true. OS enforcement of false requires Linux/macOS confinement.
  • read_only: deny mutations and allow only classified read-only shell commands.
  • instructions: load AGENTS.md or CLAUDE.md into request context.
  • note: load NOTE.md working state.
  • memory: load MEMORY.md durable facts.
  • auto_review: let the model review ask-level tool calls. Default is false.
  • prompt_modules: system prompt modules. Available names are identity, tool_discipline, working_note, and environment.

Rules

Rules match a tool name or *, optionally a normalized path subtree or command prefix. All matches participate: deny takes precedence over ask, then allow. Order does not matter. allow overrides mode defaults, not an effective explicit deny.

{
  "rules": [
    {"tool": "bash", "command_prefix": "git", "decision": "deny"},
    {"tool": "bash", "command_prefix": "git status", "decision": "allow"},
    {"tool": "write", "path_prefix": "docs/", "decision": "allow"}
  ]
}

In this example, git status is denied because the broader deny still matches. Remove or narrow that deny to allow it. Plan constraints, protected paths, and read_only win over grants and rules. External writes request additional permissions instead of being unconditionally denied. See Tools and security for scopes and approval behavior.

Hooks

Hooks run shell commands around tools. A non-zero before_tool hook denies the call.

{
  "hooks": [
    {
      "event": "before_tool",
      "command": "python tools/check_tool.py",
      "matcher": "bash",
      "timeout_ms": 10000
    }
  ]
}

event is before_tool or after_tool. matcher is a tool name, a prefix ending in *, or omitted for all tools. Hooks receive CADE_HOOK_EVENT, CADE_TOOL_NAME, CADE_TOOL_ARGS, and CADE_TOOL_RESULT in the environment.

MCP servers

MCP servers use stdio and keep one persistent connection per server.

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["mcp_server.py"],
      "cwd": ".",
      "timeout_ms": 30000,
      "env": {"LOG_LEVEL": "warn"}
    }
  }
}

Discovered tools are exposed as mcp__<server>__<tool>. They ask by default, are denied in plan mode and read-only mode, and can be allowed by a rule.

Architecture

Cade Mini is a standalone coding agent in src/cade_mini/. It uses a pipeline with four stages. Each stage has one owner and one direction of data flow.

Session log -> Conversation projection -> Request -> Run

Session log

SessionLog is an append-only JSONL file. Each entry has an ID, timestamp, type, parent ID, and data. The active branch ends at the latest entry. A tree is possible, but the loop follows one branch.

The log stores facts:

  • system, user, assistant, and tool_result are model-visible facts.
  • compaction records a summary and first_kept_id.
  • window records a new context start and an optional handoff.
  • request, run, and attempt are audit facts. They never become conversation messages.

The schema is closed and versioned. See Session log schema.

Projection

project(entries) is a pure function. It reads the branch and produces the deterministic conversation projection:

  1. Take the latest system message.
  2. Apply the latest window start.
  3. Apply the latest compaction summary.
  4. Keep retained user, assistant, and tool-result messages.
  5. Pair tool calls with tool results; insert a synthetic interrupted result at the tail when the log ends mid-call.

No projection step writes to the log. Replaying the same entries always produces the same conversation.

Request

build(conversation, tools, budget, context) admits messages into the current model window. It:

  • joins request-only context such as instructions, skill catalog, NOTE, memory, and goal;
  • preserves every projected message and tool result;
  • checks the complete request against the input budget;
  • converts the result to provider wire format;
  • returns a Request with a BuildReport.

Admission does not mutate the conversation and does not write facts. Only compaction and window events change the visible history. An over-budget request is rejected rather than silently truncated.

Run

Before appending a new user fact, run() persists interrupted results for unfinished tool calls. It does not repeat tools whose outcome is unknown. It then calls the provider, appends assistant and tool-result facts, and executes tools. It is the only stage that writes during a turn. Compaction and window fallback are decisions expressed as new log facts.

Why the split

The split prevents a common failure: the request builder starts hiding messages, then the history rewrite becomes the only copy of what happened. Mini keeps the original facts and lets the projection and admission be replaced without losing history.

Sessions and context

A session is an append-only JSONL file under .cade-mini/sessions by default. The file name is session-<id>.jsonl. The session title is derived from the first user message; no extra event type is needed.

Resume

cade-mini --list-sessions
cade-mini --continue "Continue where we stopped."
cade-mini --resume SESSION_ID "Explain the current state."

--continue and --resume open the latest or a specific session. Existing sessions keep their original system fact; a new cade-mini.json does not rewrite history. If a resumed session has no system entry, the current prompt is added.

Fork, clone, tree, and rewind

  • /clone copies the active branch into a new session.
  • /fork [N|ENTRY] copies history before a user turn (default: latest) into a new session and prints the forked input.
  • /tree lists entries; * marks the active branch.
  • /rewind [N] creates a new session without the latest N user turns.
  • /undo [N] restores the latest N file snapshots.

These operations create new sessions; they do not rewrite the original file. Compaction and window references are remapped when entries are copied.

Compaction

When the full conversation exceeds the input budget, Compactor:

  1. Selects a cut at a visible user boundary.
  2. Sends the older messages to the provider for a summary.
  3. Appends a compaction fact with the summary and first_kept_id.
  4. Reprojects the conversation as the latest system, summary, and retained tail.

Compaction is iterative: a prior summary is serialized as PRIOR SUMMARY and can be summarized again. The original user, assistant, and tool-result facts remain in the log.

Request admission

Request construction preserves the entire projection, including tool outputs. Only logged compaction and window events reduce visible history. If the request still exceeds the budget after these steps, the loop returns context_error without sending it to the provider. Use the history tool to retrieve evidence outside the current context.

Windows

A window fact starts a new context at a user entry and may include a handoff. The CLI can start one explicitly with /new-context. If compaction cannot bring a request under budget, the loop can append an automatic window with a fixed handoff that points to NOTE.md and the history tool.

History tool

history accepts one of:

  • query: case-insensitive search over the branch, returning entry IDs and snippets.
  • entry_id: exact content of one log entry.
  • call_id: exact tool result for one call.

Exact content is capped. Search results are capped and point back to entry IDs.

Request context order

For each task the request contains:

  1. The system message.
  2. Project instructions from AGENTS.md, CLAUDE.md, or their variants.
  3. The skill catalog.
  4. NOTE.md working state.
  5. MEMORY.md durable facts.
  6. An active goal.

Items 2-6 are request-only context. They are recorded in the request audit but never become conversation facts. See Architecture and the design.

How Cade Mini works

Cade Mini coordinates one model request at a time, executes the requested tools, and records every durable fact in a session log.

One run

A submitted task is appended as a user fact. Cade Mini projects the active branch, builds a request for the current budget, and sends it to the provider. The provider streams text and tool calls. The loop records the assistant message, executes each tool call, and records a tool result. If the model needs another request, the loop starts another step; otherwise the run ends.

A step is one request plus the tools caused by its response. A run can contain many steps. The loop stops on completion, a step limit, context exhaustion, cancellation, or a provider error.

Context

The projection supplies conversation history. Request-only context supplies project instructions, the skill catalog, NOTE.md, MEMORY.md, and an active goal. Tool results are pruned when they no longer fit; the history tool can read the original facts.

Compaction adds a summary fact and keeps a recent tail. A window moves the context start forward and may include a handoff. Neither operation rewrites the original messages.

Sessions

Sessions are JSONL files under .cade-mini/sessions. Entries have IDs and parent IDs, so a session can form a tree; the active branch ends at the latest entry. Resuming opens the same file and appends new facts.

Interfaces

The terminal host runs one task or a REPL. It calls the same loop and shares policy, tools, and session storage with every other entry path.

Extensions

Skills add on-demand instructions. Memory adds durable facts. Hooks run shell commands around tools. MCP adds remote tools. Subagents run an independent child session. Each extension is a narrow adapter over the loop, not a change to the session schema.

Trust and permissions

Every tool call passes through a policy. Modes, static rules, session grants, shell classification, and approvals decide whether a call runs. Linux/macOS shell and file tools also use OS confinement; Windows runs directly. See Tools and security for scopes and limitations.

See Architecture for the invariant and Capability seams for the contracts.

Relationship to Cade

Cade and Cade Mini are separate projects. This repository develops, tests, and releases only Cade Mini. It does not provide compatibility with Cade's Python package, commands, settings, credentials, or session formats.

Mini originated as a log-first implementation alongside Cade. Its provider adapters and process execution code were brought into the cade_mini package when it became independent. They are no longer shared runtime dependencies.

Mini's product boundary

Mini provides a terminal REPL and one-shot execution. Its core separates append-only session facts, deterministic projection, request admission, and the run loop.

Intentional limits include:

  • No full-screen TUI, plugin runtime, RPC, or SDK.
  • No artifact store or parallel tool scheduler.
  • No permanent approval grants; durable rules belong in project config.
  • No Windows OS sandbox; Linux uses bubblewrap and macOS uses Seatbelt.

The historical parity acceptance records workflows tested before separation. It is not a promise of future feature parity. See the code map for the current package and ownership boundaries.

Provider

The loop needs a streaming event source: text deltas, tool calls, a final message, usage, and failures. A provider owns wire conversion and replay state. Cade Mini does not depend on provider-specific message types above this seam.

Tool

A tool declares a JSON schema and an async execute. A tool result is content, an error flag, and optional metadata. Tools do not write the session log; the loop records their results.

Policy and approval

Policy returns a decision, not an execution. Approval is only consulted for ask. A denial becomes a tool error fact, so the model can recover. Keeping these separate lets the host choose a TTY prompt, a model reviewer, or a non-interactive denial.

Hooks

Hooks observe and can veto a tool call without changing the policy result. A before_tool failure is a denial; after_tool failure is ignored. Hooks are trusted configuration, not sandboxed code.

Stores

SessionLog is the durable history. SnapshotStore, GoalStore, and the memory and NOTE files are host state, not session facts. Treating them as separate stores keeps the schema closed while allowing recovery and long-term state.

Host

A host owns presentation, input, and the event loop boundary. It does not own the agent loop or the schema. The CLI renders events and runs tasks without changing either.

Tests as contracts

Each seam has a focused test module. test_mini_boundary.py enforces the import firewall, so a seam cannot quietly become a dependency on the Cade product layers.

Event model

A session is a tree of entries, not a message array. Entry types fall into two groups.

Model-visible facts

These entries project into the conversation:

Type Meaning
system Base system prompt; the latest one wins
user User task or steering input
assistant Text and tool calls produced by one model response
tool_result Result paired to a tool call

Audit facts

These entries never project:

Type Meaning
meta Session creation metadata
request Provider, model, context, digests, estimated tokens, dropped evidence
attempt One provider attempt, including failures and retries
run Termination, steps, usage, error

Audit facts make the request reproducible without turning diagnostics into conversation. A failed run therefore cannot fabricate an assistant message.

Flow

flowchart LR
  log[Session log] --> project[Projection]
  project --> conversation[Conversation]
  conversation --> request[Request build]
  request --> provider[Provider stream]
  provider --> facts[Assistant and tool-result facts]
  facts --> log
  request --> audit[request fact]
  provider --> attempts[attempt facts]
  facts --> run[run fact]

The loop appends the user fact before the first request. Each step appends one assistant fact and zero or more tool-result facts. A run appends exactly one run fact.

Ordering and pairing

A tool result follows its assistant tool call. Projection rejects an orphan result or a duplicate result. If the branch ends after a tool call without a result, projection inserts a synthetic interrupted result at the tail so the request remains protocol-valid.

Compaction and windows

A compaction cuts at a user boundary. Its summary message appears first in the retained context. A window discards earlier entries and may insert a handoff. Only the latest cut applies. Compaction is preferred; a window is a fallback when a summary cannot fit.

Schema authority

The closed schema is in Session log schema. The generated event catalog lists the current event types from code.

Tool execution

Every tool call follows the same pipeline. Policy and approval decide whether a call may run; hooks can stop it; the loop owns execution and recording.

flowchart LR
  call[Tool call] --> policy[Policy decision]
  policy -->|deny| denied[Denied tool result]
  policy -->|ask| approval[Approval]
  approval -->|deny| denied
  approval -->|allow| before[before_tool hooks]
  policy -->|allow| before
  before -->|deny| hookdenied[Hook-denied result]
  before -->|allow| execute[Execute tool]
  execute --> after[after_tool hooks]
  execute --> result[Tool result]
  result --> log[Append fact]
  denied --> log
  hookdenied --> log

Order

  1. The model returns a tool call with an ID and arguments.
  2. Policy checks tool name, path, mode, rules, grants, and shell classification.
  3. An ask decision is resolved by the host: TTY prompt, --yes, auto-review, or denial.
  4. before_tool hooks run. A non-zero exit denies the call.
  5. The tool executes within the approved per-call scope, with a timeout and cancellation token. Linux/macOS workspace tools use OS confinement.
  6. The result is truncated, appended as a tool_result fact, and rendered. Its artifact.authorization records decision, reason, and scope without adding that metadata to the model transcript.
  7. after_tool hooks run and their output is ignored.

Denials and errors

A denied call is not an exception. It becomes an error tool result so the model can adapt. Unknown tools, malformed arguments, timeouts, and thrown exceptions also become error results. A cancellation appends interrupted results for any remaining calls before the run terminates.

Hooks

Hooks receive the tool name, JSON arguments, and the result for after_tool. They run with the workspace as the current directory. A hook timeout is a denial or a silently ignored observer, never an unbounded wait.

Evidence retention

Tool results are facts. Request admission can replace old bodies with a reference that names the call_id. The history tool retrieves the exact result from the branch, so pruning does not destroy evidence.

Steering and queueing

Cade Mini's REPL can read input while a task is running. The host does not block the terminal on _run_task.

Why the old REPL blocked

The first REPL called input() in the main thread and then ran the async loop with asyncio.run. While that call was active, the terminal was not read, so /steer and /queue could only affect the next task.

Current design

stdin
  |
  v
_InputPump thread  -- _Line -->  event queue
                                  |
task thread  -- _ApprovalRequest / _TaskDone --> event queue
                                  |
                                  v
                         REPL main thread
  • _InputPump reads one line at a time and never calls the model.
  • _run_task runs in a worker thread with its own asyncio event loop.
  • The REPL main thread owns the event queue and the session state.
  • _HostApprover sends _ApprovalRequest to the main thread and waits. The main thread reads the answer from the same input pump, so approvals do not compete with a second input().
  • !command runs in the main thread and uses _ConsoleApprover, which reads the answer directly from the event queue.

Commands during a run

Input Effect
/steer TEXT Append guidance at the next model step
/queue TEXT Run TEXT as a new task after the current task
/stop or /cancel Cancel the current task at the next safe point
other text Same as /queue: run it after the current task
/exit Cancel, wait for the task to settle, then exit

/steer is not a prompt injection into a running provider request. The loop checks the steering queue before each step, appends a user fact with source: runtime, and builds the next request from the projection. This keeps the session log as the source of truth.

Queue semantics

  • A queued task starts automatically when the current task reaches a terminal state.
  • Queue order is FIFO.
  • A queued task runs in the same session; it is not a fork.
  • /fork, /clone, /rewind, and session commands are main-thread commands. They are only handled when no task is active. During a run they are treated as queued text; finish or stop the run first.

Limits

  • Tools already executing are not killed. /stop takes effect at the next cancellation check.
  • The input pump uses plain input(), not a full line editor. Editing, history, and completion are terminal features.
  • Approval answers are read as the next line. Do not type a task while an approval prompt is waiting; it is consumed as the answer.
  • The one-shot --steer flag seeds guidance before the first step. It is not a substitute for /steer during a run.

The session log

The log is append-only and versioned. It stores model-visible facts and audit facts in one tree. It is the only artifact needed to reconstruct the conversation. Compaction and windows are log entries, not rewrites.

Snapshots

Snapshots are an undo journal for file changes. They cover write, edit, and common single-command shell mutations. Format v2 uses an atomically replaced JSONL index, immutable before/after records, and content-addressed original blobs. See Snapshots and goals for conflict and legacy behavior. Snapshots are not part of the session branch.

Goals and notes

A goal is one objective with an active or done status. NOTE.md is working state that is included in every request and summarized during compaction. MEMORY.md is durable project knowledge. These files are intentionally plain: they can be edited by hand and inspected with ordinary tools.

Generated artifacts

The docs site, llms.txt, and llms-full.txt are generated from Markdown and docs.json. They are checked for freshness; do not edit the HTML by hand.

What is not persisted

  • Request-only context is recorded in the request audit, not as messages.
  • Grants last for the process; durable policy belongs in config rules.
  • Approval prompts and TUI state are host state.
  • Provider replay payloads live inside the assistant fact that produced them.

Cade Mini session schema

Current writer: v2. Readers accept v1 and v2, including mixed-version logs. This is the persistent format and projection contract.

Envelope

One JSON object per line in session-<id>.jsonl:

{"v":2,"id":"e2","parent":"e1","ts":"2026-10-18T03:00:00+00:00","type":"user","data":{"text":"Fix the test","source":"user"}}
Field Type Contract
v 1 or 2 Read both versions; append v2; reject other values
id string Unique in the file; 12 lowercase hex characters
parent string or null Previous head; null only for the first event
ts string ISO 8601 UTC timestamp
type string One of the event types below
data object Type-specific payload

The first increment has one active branch: the head is the last event. parent is stored from day one so fork and rewind do not need a schema change.

Unknown event types are a version error. Do not ignore them.

V2 payloads are validated on append and read. Unknown fields, wrong primitive types, invalid enums, and non-finite numbers are rejected. Missing optional fields are allowed but defaults are not written into the record. user.source defaults to user; assistant model/provider/usage/replay metadata and nullable artifact/handoff/usage/details fields may be absent. Cross-event call pairing and context-cut references are validated by projection. V1 keeps legacy reading rules. Branch copies preserve source event versions.

Event types

Conversation events

These produce model-visible messages.

Type Payload Projection
system {"text": str} Latest one is emitted first; never shadowed
user {"text": str, "source": "user"|"runtime"} User message at its position
assistant {"blocks": [Block], "model": str, "provider": str, "usage": object|null, "provider_state": object|null} Assistant message; empty blocks are skipped
tool_result {"call_id": str, "status": "ok"|"error"|"interrupted", "content": str, "artifact": object|null} Tool message; paired with its call
compaction {"summary": str, "first_kept_id": str, "tokens_before": int, "model": str, "provider": str, "usage": object|null, "details": object|null} Emits a summary message, then the tail from first_kept_id
window {"start_id": str, "reason": "manual"|"fallback", "handoff": str|null} Starts the projection at start_id; optional handoff summary

A block is one of:

{"type":"text","text":"..."}
{"type":"tool_call","id":"c1","name":"bash","args":{"command":"pytest -q"}}

assistant.blocks is the only record of a tool call. Do not add a separate tool_use event. The tool_result.call_id pairs with it.

A provider_state is opaque adapter data for Responses replay. It is stored on the assistant fact and passed back to the same adapter. It never enters the conversation vocabulary.

Log-only events

These are recorded but never projected.

Type Payload Purpose
meta {"session": str, "project": str, "created": str} First event; identifies the session
request {"model": str, "provider": str, "tools_digest": str, "conversation_digest": str, "context": [str], "estimated_tokens": int, "dropped": [str], "snapshot": object} Request audit; v2 adds the normalized snapshot below
run {"termination": str, "steps": int, "usage": object|null, "error": str|null} Run outcome
attempt {"model": str, "provider": str, "error": str, "usage": object|null} Failed model attempt that produced no message

The v2 request.snapshot contains messages, tools, options, budget, and report. budget records the context window, output reserve, and headroom; report records the admission result. Options omit API keys, all headers, cancellation signals, and callbacks. This is the provider-interface input, not an HTTP capture. The remaining request data is not redacted. A v1 request has no snapshot; do not infer it from current provider behavior.

A failed attempt does not become an assistant message. A run result does not duplicate the final answer; the answer is the last assistant text.

Invariants

  1. One fact, one record. A tool call appears once, in its assistant event. The final answer is not stored again.
  2. No derived content. No replacement message list, no rendered preview used as history, no display summary.
  3. Decisions are facts. A compaction cut and a window start are logged; the messages they produce are recomputed.
  4. Request context is audited, not history. Dynamic context and the request envelope live in request; only conversation events project.
  5. A compaction cut is a user turn. first_kept_id must name a user event before the compaction. A tool call and its result never cross the cut.
  6. A window start is a user turn. start_id must name a user event before the window.
  7. The latest system event wins. It is projected first and is not shadowed by compaction or a window.

Projection

project(branch) -> list[Message] is pure and deterministic.

  1. Find the latest system event. Emit it first.
  2. Find the latest window. If present, start at its start_id and keep its non-empty handoff for a summary message.
  3. Find the latest compaction at or after the window start. If present, emit its summary and start the tail at first_kept_id.
  4. Walk the retained entries in order. Emit user, assistant, and tool_result messages. Skip system, meta, window, compaction, request, run, and attempt.
  5. Pair tool calls with results by call ID.
  6. For an open call at the end, synthesize one interrupted result. Do not write it to the log. Insert it after the assistant message that contains the call.
  7. Reject an orphan result, a duplicate result, a duplicate call, a bad cut, or a bad window with ProjectionError.

Order of emitted summary messages: system, window handoff, compaction summary, retained tail.

The wire adapter renders SummaryMessage as a user-role message wrapped in <compaction-summary> or <window-handoff>. The internal role stays distinct so hosts can render it differently.

Storage

  • Directory: .cade-mini/sessions/ by default.
  • File: session-<id>.jsonl.
  • Append lock: session-<id>.lock.
  • Run lock: session-<id>.run.lock; concurrent turns are rejected.
  • Append: one line, flush, fsync.
  • Before append: truncate an incomplete trailing line from a crash.
  • On read: ignore an incomplete trailing line; reject any earlier invalid line.
  • Reject duplicate IDs and forward parent references.
  • No rewrite, no in-place edit.

Compaction record

{"v":2,"id":"e80","parent":"e79","ts":"...","type":"compaction",
 "data":{"summary":"## Goal\n...","first_kept_id":"e52","tokens_before":48210,
         "model":"gpt-5.6-luna","provider":"chatgpt",
         "usage":{"input":43000,"output":1200},"details":null}}

The summary is model-generated content and must be logged. The original events before first_kept_id stay in the log. A later compaction starts after the previous one and may include the previous summary in its input.

Window record

{"v":2,"id":"e90","parent":"e89","ts":"...","type":"window",
 "data":{"start_id":"e88","reason":"manual","handoff":"Optional note."}}

A window is the hard fallback. Compaction is the default. A window is explicit through /new-context, or automatic when compaction cannot reduce enough.

Versioning

v is the only compatibility switch. A change to an existing payload, a new conversation event type, or a change to projection semantics requires a new v and a migration note. Adding a log-only event type is a new v as well, because older readers must reject it rather than ignore it. See the upgrade guide for v1 resume and rollback.

Log

SessionLog owns the append-only JSONL file.

Create and open

  • SessionLog.create(directory, session_id=None) creates a unique file and writes a meta entry.
  • SessionLog.open(path) validates the envelope and v2 payloads. Reads ignore a torn final line; the next valid append truncates that tail.
  • The session ID is derived from the file name when not supplied.

Append

append(type, data):

  1. Validates the v2 payload without modifying the file.
  2. Takes an exclusive file lock.
  3. Repairs a torn tail and reads the current entries to get the parent ID.
  4. Builds an entry with ID, timestamp, parent, type, and data.
  5. Appends one JSON line, flushes, and calls fsync.
  6. Releases the lock.

fsync is deliberate: a returned append is durable enough to resume. A failed write raises LogError and does not return a fake entry.

run_lock() protects a whole turn separately from individual appends. It rejects competing operations immediately with LogError. run() and manual CLI context changes use it; other multi-event storage clients must acquire it explicitly.

Branch

branch() follows parent IDs from the last entry back to the root and reverses the list. It rejects cycles, missing parents, and duplicate IDs.

Listing and titles

list_sessions(directory) returns session ID, update time, and a title derived from the first user text. Corrupt files are skipped so one bad session cannot break the list.

Invariants

  • Entries are never rewritten in place.
  • IDs are unique within a file.
  • A parent precedes its child.
  • The file ends with exactly one newline.
  • The schema version is closed; new event types require a decision record.

Projection and request

Projection

project(entries) is pure. It:

  1. Finds the latest system entry.
  2. Applies the latest window start.
  3. Applies the latest compaction cut and emits a summary message.
  4. Converts user, assistant, and tool-result facts to messages.
  5. Pairs each tool call with its result by call ID.
  6. Inserts a synthetic interrupted result if the branch ends inside a call.

It rejects orphan results, duplicate results, and cuts that do not point to a user entry. The projection does not call a provider or write the log.

Request

build(conversation, tools, budget, context):

  1. Joins the base system prompt with request-only context.
  2. Estimates tokens.
  3. Preserves all projected messages and tool bodies.
  4. Converts to provider messages and tool definitions.
  5. Returns a Request and a BuildReport.

BuildReport records estimated tokens and budget. Legacy dropped-call and turn counters remain empty/zero. require_sendable() raises RequestTooLarge when the full request cannot fit. The loop reduces context only through logged compaction and window decisions, then rejects any remaining overflow.

Context order

The system message carries base instructions plus, in order: instructions, skill catalog, NOTE, memory, and goal. These inputs are request-only; the v2 request audit records their full text, the admitted messages, tool definitions, non-authentication options, and budget. Session files can contain sensitive input.

Tests

test_mini_projection.py, test_mini_request.py, and test_mini_compaction.py cover cuts, strict admission, and wire-format contracts.

Loop

run(log, text, ...) is the only stage that writes during a turn.

One run

  1. Append the user fact.
  2. For each step:
    • Project the branch.
    • If the full estimate exceeds budget, call the compactor.
    • Build the request.
    • If still over, call the window fallback.
    • Append a request audit fact.
    • Stream the provider.
    • Append the assistant fact.
    • Resolve and execute each tool call.
    • Append tool-result facts.
  3. Append one run fact with termination, steps, usage, and error.

Provider handling

The loop collects text deltas, tool calls, usage, and provider replay state. A failure becomes an attempt fact. Retryable failures are retried once by default; the retry delay is configurable. A terminal failure ends the run with provider_error and never creates an assistant fact.

Termination

  • completed: the provider ended without tool calls.
  • step_limit: the configured step count was reached.
  • context_error: no request fits after compaction and window fallback.
  • aborted: cancellation was requested.
  • provider_error: the provider failed.

Cancellation

A cancellation token is checked between steps and tool calls. Running tools get the token; remaining calls receive interrupted results. The run records the reason in its run fact.

Events

The host receives text deltas, tool start, tool end, and final output. Events are presentation; facts are durable. A host can drop events without losing history.

Tests

test_mini_loop.py covers completion, tool use, approvals, retries, timeouts, cancellation, context errors, and window fallback.

Tools and policy

Contracts

A tool declares a name, description, JSON schema, and async execute. The loop records content and the error flag; tools do not append session facts.

core.permissions.Policy.check returns a PermissionCheck with a decision (allow, deny, or ask), reason, and ExecutionScope. authorize resolves only asks using an ApprovalRequest and ApprovalResult. The loop and CLI direct-shell path use the same authorization function.

WorkspacePolicy applies mode constraints and protected paths before explicit rules, grants, and mode defaults. Matching rules use deny > ask > allow. Subagent modes cannot expand parent permissions. See Tools and security for user-facing semantics.

Execution

The loop installs the authorized scope in a context variable only while the specific tool runs. This scope is preserved across async tasks and worker threads and reset afterward. It never changes the default workspace or grants.

The CLI constructs a PlatformSandbox with the project root, private temp, network setting, and protected paths. SubprocessShell wraps commands before spawning. File tools use the same backend through tools._worker; snapshot storage remains host-owned. External file changes have no workspace snapshot. Cancellation signals reach the subprocess launcher, and tools wait for process termination before returning or cleaning up request files.

Linux uses bubblewrap, macOS uses Seatbelt, and Windows runs directly. Backend errors become tool errors, not unsandboxed retries. Hooks and MCP server processes are trusted host extensions outside this boundary.

Reviewer

AutoReviewer receives the authorization reason, exact arguments, retained conversation, ancestor conversations, and context constraints. It uses a separate tool-free request. Oversized input is rejected rather than silently truncated. Output is a strict object with allowed: bool and reason: str. Rejections and failures return their reasons to the model as tool errors.

Context and compaction

Request context

The system message is the base prompt plus request-only context:

  1. Project instructions from AGENTS.md, CLAUDE.md, or variants.
  2. Skill catalog names and descriptions.
  3. NOTE.md working state.
  4. MEMORY.md durable facts.
  5. An active goal.

The request audit records this context and the normalized request; it does not turn the text into conversation facts.

Compaction

Compactor runs when the full projection exceeds the input budget.

  1. Select the cut at a user boundary that keeps the recent tail under the configured target.
  2. Serialize older messages, including a prior summary.
  3. Ask the provider for a summary with a bounded output.
  4. Append a compaction fact with summary and first_kept_id.
  5. Reproject.

A summary failure or a cut with no messages appends an attempt fact and leaves the conversation unchanged. A prior summary is included as PRIOR SUMMARY, so compaction is iterative.

Window fallback

If compaction cannot fit, the loop may call the window hook. The CLI starts a window at the latest user entry with a fixed handoff that points to NOTE.md and history. If the request still does not fit, the run terminates with context_error.

History

The history tool searches the branch or reads an exact entry or tool result. It retrieves evidence outside the current compaction or window boundary. Exact content is capped; search results point to entry IDs.

Request admission

Admission preserves the full projection. Overflow requires a logged context transition or fails with context_error. See Projection and request.

Tests

test_mini_compaction.py, test_mini_window.py, test_mini_history.py, and the request tests cover cuts, summaries, fallback, and retrieval.

Extensions

Extensions add behavior through narrow seams. None changes the session schema.

Skills

Discovery reads SKILL.md from user and project roots. The request carries a catalog; the skill tool loads a body into a tool result. A body is a fact, not request-only context.

Memory

MEMORY.md is request context. The memory tool appends one bullet and cannot write other paths. The file is capped to protect the request budget.

Hooks

HookRunner executes configured shell commands around tools. before_tool can deny; after_tool observes. Hooks are trusted and time-bounded. See Hooks, MCP, and subagents.

MCP

Each configured stdio server keeps one persistent process. Discovery reads tools/list; calls use tools/call over a serialized queue. Tools are prefixed mcp__, ask by default, and are denied in plan and read-only modes. A server that cannot start is reported and skipped.

Subagents

SubagentTool creates a child session under <sessions>/subagents. The child gets the parent provider, budget, policy, approver, hooks, context, and base tools plus its own history. It cannot spawn another subagent and is limited to 20 steps. The parent records only the call and summary. DelegateTool runs one or more child tasks sequentially and optionally applies a more restrictive child mode. Reviewer requests retain ancestor conversations so a child prompt cannot replace human restrictions.

Snapshots

SnapshotStore captures write, edit, and common single-command shell mutations. --undo and /undo restore the latest snapshot. Snapshots are project state, not session facts.

Goals

GoalStore persists one objective in .cade-mini/goal.json. The goal tool and /goal command manage it. An active goal is request context.

Hosts

The CLI runs one-shot and REPL sessions. It uses the same loop and policy as every other entry path.

Limits

Extensions are deliberately small. MCP is a stdio client, not a full capability negotiation implementation. Hooks are shell commands, not in-process callbacks. Subagents are sequential and share the parent approval context.

Tools and security

Workspace tools

  • read: read a UTF-8 file or list a directory. Output is capped.
  • write: write UTF-8 text and create parent directories.
  • edit: replace one exact occurrence of old text.
  • glob: list workspace files matching a glob.
  • grep: search workspace text files with a regular expression.
  • bash: run a shell command, optionally with a workdir and additional_write_paths that request extra permissions for this call.

The workspace is the fixed project root, not the shell's current directory or an alias for the entire home directory. Reads can use external paths, except protected files. Workspace writes have snapshots; external writes do not.

Modes

  • build is the default. Normal edits, tests, builds, and shell pipelines run automatically. Detected destructive, privileged, publishing, or external-send operations require approval.
  • ask allows classified read-only operations and asks before changes or unclassified shell commands.
  • plan supports exploration and discussion, not implementation. Project changes, memory changes, goal changes, and MCP calls are denied. File tools can write under <workspace>/.cade-mini-plans/ only after approval for a user-requested plan. Implementation requires the user to switch modes.

Subagents inherit the parent's limits. A child mode can only narrow them. --read-only and --sandbox read-only deny mutations while allowing classified read-only shell commands. These constraints cannot be overridden by rules, grants, --yes, or Reviewer approval.

Rules and grants

Rules in cade-mini.json match a tool, normalized path subtree, or command prefix. All matching rules participate: deny wins over ask, which wins over allow. An explicit allow overrides a default ask, not an effective deny. Remove or change a deny rule to revoke it; an approval answer cannot do that.

A TTY answer of a creates a process-local session grant. File grants match the same tool and path. Shell grants also match workdir and extra write paths; MCP grants match the complete arguments. A grant can answer an ask but cannot bypass a deny. /permissions lists grants; /permissions clear removes them.

Approvals and Reviewer

Only an ask enters approval:

  • --yes approves asks, not denials.
  • --auto-review sends the pending action, authorization reason, retained conversation, parent conversations, and context constraints to a tool-free Reviewer call. The response must contain a strict boolean allowed and a non-empty reason.
  • Otherwise, a TTY prompts for y once, n deny, or a always.
  • Without an available approver, the action is denied.

Reviewer rejection, timeout, provider failure, and malformed responses become error tool results with reasons. They return to the acting model without an automatic human prompt. The model must respect the denial while adjusting its approach. Reviewer does not inspect every ordinary development operation.

Shell classification and risk detection are conservative heuristics, not a security boundary or a complete analysis of arbitrary scripts. They cannot identify every destructive or external effect hidden inside programs.

OS sandbox

Filesystem scope is independent of mode and approval:

Policy Scope
workspace-write (default) Write in the project and private session temp directory
read-only No regular file writes
danger-full-access Skip OS confinement; explicit deny rules still apply

Linux uses installed bwrap (bubblewrap). macOS uses system sandbox-exec (Seatbelt). Missing backends and startup failures return tool errors; neither platform silently retries without confinement. Windows skips OS confinement and retains application policy and approval checks without extra prompts.

The CLI routes shell commands and file tools through the same execution policy. On Linux/macOS, file tools execute in a fixed-operation sandboxed Python worker. Approving an external file write grants that target for this call. Shell additional_write_paths must name existing files or directories; a directory grant includes its descendants. Changing workdir does not expand write permissions. Approvals never silently grant full host access.

Network access is independent and enabled by default. --no-network disables sandbox network access; approving network access does not grant external file writes. Windows and danger-full-access do not provide OS-level network restriction. The provider connection runs outside the tool sandbox.

On Linux/macOS, the CLI hides existing user and project .cade-mini directories from sandboxed commands and protects existing Git hooks and Git configuration from writes. The home directory is not writable by default. Private temp and common tool caches are redirected to a session directory, cleaned on exit. Apart from hidden paths, the filesystem remains readable; this is not complete secret isolation. Restrict credentials and exposed resources accordingly.

Hooks, MCP server processes, and host-managed state run outside the tool sandbox. Treat their configuration and code as trusted. The sandbox is not a container or VM, and it does not make an untrusted repository safe.

See decision 0009 for the contract.

Snapshots and goals

File snapshots

Cade Mini records a snapshot before a file tool changes a file. Snapshots live under .cade-mini/snapshots with a JSONL index and one directory per snapshot.

Covered changes:

  • write and edit.
  • Common single-command shell mutations: rm, mv, cp, touch, mkdir, redirection with >, and sed -i.
  • Creating a file records that it did not exist; undo removes it.

Not covered:

  • Complex pipelines, command lists, unknown scripts, and commands that mutate files without naming them.
  • Files larger than the snapshot limit (5 MiB) are rejected rather than silently skipped.
  • Directory trees are not copied; directory mutations are skipped.

Undo

cade-mini --undo

This restores the latest snapshot and exits without contacting a provider. In the REPL, use /undo. Each call restores one snapshot, so repeated undo walks back through the recorded changes. Stop external file writers before undo.

Undo checks that the current file matches the recorded post-change state. It rejects conflicts, corrupt payloads, and snapshots whose outcome is unknown. A rejected undo leaves the file and index unchanged. Legacy snapshots have no post-change state and require manual inspection; automatic undo rejects them.

Snapshots are project state, not session facts. They are not part of the JSONL session branch.

Goals

A goal is one durable objective stored in .cade-mini/goal.json. It has an objective, a status (active or done), and an update time.

cade-mini --goal "Add a regression test for the parser" "Start the task."

In the REPL:

  • /goal shows the current goal.
  • /goal TEXT sets an active goal.
  • /goal done marks it complete.
  • /goal clear removes it.

The goal tool provides the same actions to the model. An active goal is added to request context so a resumed or compacted session still knows the objective. Goals are host state; they do not change the session schema.

Goals are intentionally small. Use NOTE.md for working details and MEMORY.md for facts that outlive the objective.

Skills and memory

Skills

Cade Mini discovers SKILL.md files in two roots:

  1. ~/.cade-mini/skills/<name>/SKILL.md for user skills.
  2. <project>/.cade-mini/skills/<name>/SKILL.md for project skills.

Later roots override earlier roots with the same skill name. A skill file can start with YAML frontmatter:

---
name: release-check
description: Validate release metadata before tagging.
---

Run the release checklist...

name defaults to the parent directory. description defaults to the first non-empty body line. Invalid names and empty bodies are skipped.

The request gets a compact <available-skills> catalog with names and descriptions. The model loads a body on demand with the skill tool:

{"name": "release-check"}

Skill bodies are facts in the tool result, not request-only context. Loading the same skill twice is harmless but adds another tool result.

Memory

MEMORY.md at the project root stores durable facts. It is loaded into request context as <memory source="MEMORY.md"> on every task, capped at 32 KiB.

The model appends facts with the memory tool:

{"text": "Prefer pytest and keep changes minimal."}

memory writes only MEMORY.md; it cannot write arbitrary paths. The file is capped at 64 KiB for writes. Remove stale entries manually when it fills.

Memory is different from the other state files:

  • AGENTS.md is project instruction, owned by the project.
  • NOTE.md is short-lived working state; it is summarized with compaction.
  • MEMORY.md is a durable preference or convention.
  • The session log is the record of what happened.

Request context

Instructions, skill catalog, NOTE.md, MEMORY.md, and an active goal are all request-only context. They appear in each request audit but never become conversation messages. See Sessions and context.

Hooks, MCP, and subagents

Hooks

Hooks run shell commands around tools. They are configured in cade-mini.json:

{
  "hooks": [
    {
      "event": "before_tool",
      "command": "python tools/check_tool.py",
      "matcher": "bash",
      "timeout_ms": 10000
    }
  ]
}
  • before_tool runs after policy and approval, before the tool executes. A non-zero exit denies the call and records an error tool result.
  • after_tool runs after a successful or failed executed tool. Its output is ignored.
  • matcher is an exact tool name, a prefix ending in *, or omitted for all.
  • Commands run with the workspace as the working directory and receive CADE_HOOK_EVENT, CADE_TOOL_NAME, CADE_TOOL_ARGS, and CADE_TOOL_RESULT.

Hooks are trusted configuration. A hook that hangs is killed after its timeout.

MCP

MCP servers use stdio. Cade Mini starts one persistent process per server and discovers its tools at startup:

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["mcp_server.py"],
      "timeout_ms": 30000
    }
  }
}

Tools are named mcp__<server>__<tool>. Their input schema comes from the server's tools/list response. Calls run sequentially over the connection and preserve server state.

Policy:

  • plan mode hides MCP tools and denies them.
  • read_only denies them.
  • build and ask ask by default; a rule can allow a specific tool.

A server that fails to start is reported at startup and skipped. Connections are closed at process exit.

Subagents

The subagent tool runs one child task in its own session and returns the final answer with the child session ID:

{"prompt": "Find the failing test and report the file and line."}

The child:

  • gets the parent's provider, budget, policy, approver, hooks, and request context;
  • gets the base tools plus a history tool bound to its own log;
  • does not get another subagent tool, so it cannot recurse;
  • uses at most 20 steps;
  • writes its own session under <sessions>/subagents/.

The parent records only the tool call and the returned summary. The child log keeps the detailed evidence.

delegate uses the same runner for one or more tasks:

{"tasks": ["Inspect the parser", "Add a regression test"], "mode": "build"}

Tasks run sequentially in separate child sessions. Each result includes the child session ID; the parent gets one combined tool result. Child modes cannot expand parent permissions: a Plan parent cannot delegate Build work.

Limits

MCP is a small stdio client, not a full capability negotiation implementation. Hooks are shell commands, not in-process callbacks. Subagents are sequential and share the parent's approval context rather than running in parallel.

Cookbook

Procedures with a concrete outcome and a verification step. Each recipe names the mode and the evidence to keep.

  • Fix a bug: reproduce, patch, verify, report.
  • Add a feature: test, implement, verify, review the diff.
  • Review only: investigate in plan mode without mutations.
  • Run a long session: NOTE, compaction, history, and goals.
  • Connect a custom MCP server: configure, allow, call, inspect.

For command details, see CLI and Configuration.

Fix a bug

Use build mode for the change. Keep the patch minimal and verify with the repository's tests.

Procedure

  1. Reproduce the failure:

    cade-mini --mode plan "Read the failing test and explain the failure."

  2. Fix it:

    cade-mini --mode build --yes "Fix the failing test with the smallest change, then run pytest."

  3. Inspect the diff and the snapshot:

    git diff
cade-mini --undo  # only if the change is wrong

Verify

  • The targeted test passes.
  • The full relevant test file passes.
  • The diff contains only the intended change.
  • The assistant names the command it ran.

Keep

The run log records the request, tool calls, and test output. The snapshot allows recovery before the next run. For a reviewable change, keep the diff in the commit, not in a docs file.

Avoid

  • --read-only when you intend to edit.
  • --yes on a shared repository without rules.
  • A broad refactor when a one-line condition fixes the test.

Add a feature

Write the test first, then implement, then verify. Use build mode and keep the diff reviewable.

Procedure

  1. Ask for a failing test or write it yourself:

    cade-mini --mode build --yes "Add a test for mul() that asserts 2 * 3 == 6; run it and confirm it fails."

  2. Implement the smallest change:

    cade-mini --mode build --yes "Implement mul() and run the new test."

  3. Review:

    git diff
pytest -q

Verify

  • The new test fails before the change and passes after it.
  • Existing tests still pass.
  • The implementation has no unrelated edits.
  • Public behavior is documented in the relevant guide.

Undo

If the change is wrong, use cade-mini --undo or /undo before starting another attempt. Undo restores one recorded file change at a time.

Keep

Update the guide or decision record when the feature changes a public contract. Tests belong in tests/; docs belong under docs/.

Review only

Use plan and --read-only when the task is to inspect, not change.

Procedure

cade-mini --mode plan --read-only "Review the request builder for evidence loss. Cite files and lines; do not modify anything."

Plan mode hides write and edit tools and denies mutating shell commands. --read-only also denies memory, MCP, and any remaining mutation.

Verify

  • git status is clean.
  • The answer cites files by relative path and line.
  • Claims about tests name the command and result.
  • Findings distinguish a bug from a preference.

Keep

For a review, keep the report in the conversation or a review document. Do not create a working note unless the review spans multiple sessions.

Limits

The model can still read anything inside the workspace. A review of untrusted code still needs human judgment; the policy prevents writes, not misleading prose.

Run a long session

Long tasks need durable state and a way to recover context. Use NOTE.md, a goal, and the history tool.

Procedure

  1. Set a goal:

    cade-mini --goal "Migrate the request builder to the new budget model" "Start by mapping the current admission rules."

  2. Keep a working note. Ask the model to update NOTE.md after each milestone:

    Update NOTE.md with completed work, current blockers, and the next action.

  3. Continue the same session:

    cade-mini --continue "Resume from NOTE.md and run the next step."

  4. Compact when the session grows:

    /compact

  5. Recover an old detail:

    Use history with query "budget" to find the earlier discussion.

Verify

  • NOTE.md names the next action, not just history.
  • A resumed run can continue without the original terminal.
  • The goal is marked done only when its acceptance check passes.

Limits

NOTE.md is request context and is summarized during compaction. MEMORY.md is for durable facts, not a task log. The session log is the authority for exact evidence.

Connect a custom MCP server

MCP servers use stdio. Cade Mini keeps one process per server and exposes each tool as mcp__<server>__<tool>.

Configure

Add the server to cade-mini.json:

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["tools/mcp_files.py"],
      "timeout_ms": 30000,
      "env": {"LOG_LEVEL": "warn"}
    }
  }
}

command and args are required; cwd, env, and timeout_ms are optional. A relative cwd resolves against the project root.

Allow

MCP tools ask by default. Add a rule for a specific tool if unattended runs need it:

{
  "rules": [
    {"tool": "mcp__files__read_file", "decision": "allow"}
  ]
}

Plan mode and --read-only deny MCP tools even with a rule.

Verify

  1. Start Cade Mini; it prints a startup error if the server cannot start.
  2. Ask the model to list or call a discovered tool.
  3. Check the tool result and the mcp__ prefix in the log.
  4. Stop Cade Mini; the server process closes at exit.

Limits

The client implements initialize, tools/list, and tools/call. It does not implement resources, prompts, sampling, or server-initiated requests. A server that hangs is killed after the configured timeout.

Hosts

Cade Mini has one host: the terminal CLI. It uses the session log, request builder, tools, and policy.

Terminal

Without a task, the CLI starts a REPL:

cade-mini

The REPL prints tool progress to stderr, streams assistant text to stdout, and accepts the commands listed in CLI. With a task, it runs once and exits:

cade-mini "Fix the failing test."
cade-mini exec "Fix the failing test."

One-shot mode supports --json for a JSONL event stream. The REPL does not.

Cade Mini review standards

This document defines how coding agents should review this repository. It is separate from implementation standards: AGENTS.md and code standards guide how to write code; this file guides how to judge code.

Review Goal

Review code for correctness, maintainability, Pythonic design, clean boundaries, and long-term elegance.

Do not treat “tests pass” as sufficient. Passing tests only prove current behavior under current coverage. A review must also judge whether the code is simple, well-shaped, and worth keeping.

Prefer fewer high-quality findings over many minor comments.

Review Scope

Check for:

  • serious bugs and edge-case failures;
  • architecture and module-boundary problems;
  • security risks and unsafe defaults;
  • non-Pythonic or awkward implementation patterns;
  • unnecessary abstraction, compatibility layers, indirection, or defensive code;
  • duplicated helpers or concepts;
  • APIs shaped for tests rather than real usage;
  • tests that overfit implementation details;
  • code that works but is not clean, separable, or elegant.

Core Principles

Code should be Pythonic, explicit, typed, and easy to reason about.

Prefer direct design over compatibility scaffolding. Do not preserve backward compatibility unless there is an explicit project requirement.

Tests serve production code. Do not accept awkward production APIs, leaked internals, or distorted boundaries merely because existing tests expect them.

A clean deletion is often better than preserving unused flexibility.

A small amount of duplication is better than premature abstraction. Abstraction is justified only when it clarifies a real shared concept.

Avoid “just in case” design. Flexibility without a concrete caller is usually noise.

What To Flag

Flag code when it:

  • hides simple logic behind unnecessary helpers, classes, registries, factories, or protocols;
  • mixes unrelated responsibilities in one module or class;
  • creates compatibility paths that are not required by current users;
  • uses dynamic imports, untyped escape hatches, broad exception swallowing, or loose dictionaries where typed structures would be clearer;
  • makes tests depend on private implementation details instead of observable behavior;
  • changes production design only to make tests easier;
  • adds comments that explain obvious code instead of clarifying real constraints;
  • introduces dependencies, config, or runtime behavior that is broader than the actual need;
  • duplicates concepts under different names;
  • keeps dead code, unused extension points, or speculative branches.

What Not To Flag

Do not report pure personal taste.

Do not nitpick formatting that Ruff or the formatter should handle.

Do not request abstraction merely because two pieces of code look similar. First decide whether they express the same concept.

Do not demand backward compatibility unless the repository explicitly requires it.

Do not treat test failures as automatically meaning production code is wrong; the test may be the thing that should change.

Finding Format

Each finding should include:

  • severity: critical, high, medium, or low;
  • file path and symbol;
  • the problem;
  • why it matters;
  • the cleanest recommended direction.

Use direct language. If something exists only for compatibility, test convenience, or accidental complexity, say so.

Prefer this format:

[medium] src/cade_mini/example.py::ExampleRunner

Problem:
...

Why it matters:
...

Recommended direction:
...

Severity Guide

Use critical for issues that can cause data loss, security exposure, command execution risk, or completely broken core behavior.

Use high for likely runtime bugs, incorrect behavior in normal use, unsafe architecture, or design that blocks future work.

Use medium for maintainability problems, unclear boundaries, bad abstractions, fragile tests, or non-Pythonic design that will likely create bugs later.

Use low for local cleanup opportunities that improve clarity but do not currently distort the design.

Do not inflate severity to make a point.

Review Output Rules

Do not modify files during review.

Do not produce a long list of minor style comments.

Group related findings when they share the same root cause.

Include file paths and concrete examples.

If the code is mostly good, say so and report only meaningful issues.

If a finding depends on an assumption, state the assumption.

0001: Compaction cut pointed at a shadowed user entry

Date: 2026-10-18

Status: resolved

Impact

After a prior compaction, the next compaction could choose a first_kept_id from a user entry that was already shadowed. The summary covered the wrong tail, and the retained window could omit the current task.

Timeline

  • The compactor collected all user entries from the branch.
  • It collected user positions from the visible projection.
  • It chose a cut by visible position but indexed the full branch entry list.
  • A session with a prior compaction therefore pointed at an older, shadowed user entry.

Root cause

Two lists with different lengths were treated as parallel arrays. A compaction removes old user entries from the projection but leaves them in the branch. The index into visible positions is not an index into all branch users.

Fix

The compactor now aligns with the last N user entries, where N is the number of visible user messages. A regression test builds a session with a prior summary, a retained turn, and a new task, then asserts the new cut points at the new task and the summary request contains the prior summary.

Verification

test_mini_compaction.py::test_iterative_compaction_includes_prior_summary passes. The projected roles are system, summary, user.

Follow-up

Any future cut logic must derive entry IDs from the same visible sequence it uses to choose positions. See Context and compaction.

0002: One huge tool result exhausted the request budget

Date: 2026-10-18

Status: resolved

Impact

A single tool result larger than the input budget could make a request impossible. The request builder protected the most recent four tool results, so a lone huge result was never replaced, and the run ended with context_error.

Timeline

  • A tool returned a result larger than the budget.
  • Admission protected the result because it was among the latest four.
  • Turn dropping removed old turns but not the current turn's huge result.
  • The request remained over budget and the run failed.

Root cause

The pruning policy treated "recent" as always protected. Protection is a heuristic for preserving working evidence, not a hard invariant. With only one result, the protected set was the entire candidate set.

Fix

Admission now prunes in passes:

  1. Replace unprotected results, oldest first.
  2. If still over, replace protected results oldest first.
  3. If still over, replace the newest result as a last resort.

Every replacement points to the history tool, so the evidence remains retrievable. A regression test covers a single huge result.

Verification

test_mini_request.py::test_build_prunes_a_single_huge_tool_result passes and the resulting request is under budget.

Follow-up

Keep the history tool available whenever pruning can remove the newest result. See Projection and request.

2. The core idea and the primary invariant

One sentence: Cade keeps a durable, inspectable record of what happened, and gives the model a deterministic view of that record, while effects happen only through typed tools.

The working rule is the one Dsh states as model-visible means logged: every model-visible message must be reconstructable from the session log. A new model-visible input needs a logged fact. A log-only record is allowed, but it never projects into model history.

Four invariants:

  1. Facts are durable and append-only. User input, model output, tool results, and compaction decisions are recorded before they are relied on. Recovery is re-derivation, not reconstruction from process memory.
  2. History is a projection. project(log_branch) -> conversation is pure, deterministic, and independent of process state. It contains no stored projection and no mutable working copy.
  3. A request is a snapshot. build(conversation, context, tools, budget) -> request is pure. It may drop content to fit the budget and reports what it dropped. It never writes history.
  4. Effects go through tools under policy. The loop decides what to call; the policy decides whether it may start; the workspace is the effect surface.

The differentiating part is invariants 1 and 2. A streaming loop, tool parsing, and file tools are table stakes. The lossless transcript behind a lossy window, the branchable session, and the auditable request are Cade's identity.

Three planes, one log

The log contains three kinds of records. Only the first is projected:

Plane Examples Projected? Purpose
Conversation user, assistant, tool_result, system, compaction Yes Model-visible history
Request request No Exact request envelope, dynamic context, token estimate, dropped ids
Operational run, attempt, window, meta No Lifecycle, failures, hard boundaries, metadata

window is a decision that changes where projection starts. It is log-only because it produces no message of its own; an optional handoff summary is a separate conversation fact.

The latest system event is always projected first and is never shadowed by compaction. Log a new one when the base prompt changes. Dynamic context such as the environment, AGENTS.md, and the current mode is request-only.

This separation satisfies "model-visible means logged" without pretending that the current environment, AGENTS.md, or a failed attempt is conversation.

Record shapes

One JSON object per line. A branch is a parent chain; the head is the last entry.

{"v":1,"id":"e1","parent":null,"ts":"...","type":"meta","data":{"session":"s1","project":"C:/repo"}}
{"v":1,"id":"e2","parent":"e1","ts":"...","type":"user","data":{"text":"Fix the test","source":"user"}}
{"v":1,"id":"e3","parent":"e2","ts":"...","type":"assistant","data":{"blocks":[{"type":"text","text":"..."},{"type":"tool_call","id":"c1","name":"bash","args":{"command":"pytest -q"}}],"model":"...","provider":"...","usage":{"input":1200,"output":80},"provider_state":null}}
{"v":1,"id":"e4","parent":"e3","ts":"...","type":"tool_result","data":{"call_id":"c1","status":"ok","content":"3 passed"}}

A system event carries {text}; the latest one is projected first. A summary message is emitted from a compaction event, not stored as a message.

3. The one-way pipeline

Session log (conversation + request + operational facts)
      │  project()            pure; reads conversation facts and window decisions
      ▼
Conversation (immutable)
      │  build()              pure; adds request-only context; admits to budget
      ▼
Request (ephemeral) ────────► provider
      │
      ▼
Tool calls ──► effects ──► tool results ──► append to log

Definitions:

  • Log is an ordered set of typed facts on a branch.
  • Project(log) -> Conversation is pure and deterministic. It rejects a malformed branch with a specific error.
  • Build(conversation, context, tools, budget) -> Request is pure. It reports what it dropped; it does not write.
  • Run(log, input) -> events + new facts is the only writer.

Rules:

  • R1. One fact, one record. A tool call appears in the assistant fact, not twice. The final answer is the last assistant text, not a separate fact.
  • R2. No derived content in the log. A stored message list, a rendered preview used as history, or a display summary is not a fact. Large tool output may live in an immutable blob; the log stores a stable reference, and the projection resolves it.
  • R3. Decisions are facts; projections are not. A compaction boundary or a window start may be logged. The messages they produce are recomputed.
  • R4. Request context is logged but not projected. The base system prompt is a system conversation fact when it changes. Dynamic context, the model route, tool schemas, token estimates, and dropped ids are request facts.
  • R5. Failures are log-only. A failed attempt is an attempt fact. It does not become a fake assistant message.
  • R6. Budget admission belongs to the request. Compaction belongs to the loop, because it appends a fact. A request builder never calls a model.

4. Current leaks

These are the back-edges that make the current code hard to maintain.

  1. The projection is written into the log. A rollover stores the complete encoded replacement surface in context_window_reset (recorder.py record_context_window_reset, surface.py applies replacement at replay). Replay then depends on output produced by an older version of the projection code, not only on facts.
  2. Request assembly mutates history. DefaultRequestAssembler.assemble rewrites context.messages in place (request.py). call_provider appends a ContextMessage to history while sending the request (_provider.py). Request construction is therefore also a state update.
  3. One fact is recorded several times. The final answer is stored again in the final event and in an assistant record, on top of the assistant event's text; replay de-duplicates it with a heuristic (recorder.py, surface.py _append_plain_assistant). Tool calls are stored inside the assistant event and again as tool_use events (events.py), then de-duplicated by call ID at replay.
  4. Three event vocabularies. AgentEvent becomes AgentHarnessEvent, then a versioned session envelope (event_codec.py). Each boundary is a translation layer that can drift from the log.
  5. History is a mutable working state. ContextManager.history holds both the projection and the loop's writes; replay loads into it (context_manager.py, replay.py). There is no runtime boundary between "what the log says" and "what this process currently has".

5. Compaction and window

Compaction and window switching are projection semantics. They belong in the first increment because a coding session outgrows one model window. The full event schema and storage contract are in Session schema.

Compaction

A compaction is a conversation fact and a decision:

{"v": 1, "id": "e80", "parent": "e79", "ts": "...", "type": "compaction",
 "data": {
   "summary": "## Goal\n...\n## Progress\n...\n## Next steps\n...",
   "first_kept_id": "e52",
   "tokens_before": 48210,
   "model": "gpt-5.6-luna",
   "provider": "openai-codex",
   "usage": {"input": 43000, "output": 1200},
   "details": {"read_files": ["src/a.py"], "modified_files": ["src/b.py"]}
 }}

Projection rule:

  1. Project the latest system event first. It is never shadowed.
  2. Find the latest compaction on the branch.
  3. Emit its summary as a summary message. The wire adapter renders it as a user-role message wrapped in <compaction-summary>.
  4. Project conversation facts from first_kept_id to the head.
  5. Ignore the shadowed facts for this projection. They remain readable in the log.

Compaction is chosen at a user-turn boundary so a tool call and its result never cross the cut. The retained tail starts with a complete user turn. If the latest turn alone exceeds the budget, use a window instead of splitting the turn.

Repeated compaction is iterative: the next compaction starts after the previous one, includes the previous summary in its input, and appends a new summary with a new first_kept_id. Projection uses only the latest compaction.

Window

A window is a hard start with an optional handoff:

{"v": 1, "id": "e90", "parent": "e89", "ts": "...", "type": "window",
 "data": {"start_id": "e88", "reason": "manual", "handoff": "Optional note."}}

Projection starts at start_id after the latest system event. If handoff is present, emit it as a summary message before the start. The window event itself is log-only.

When each runs

  • Automatic compaction runs before a request when the estimated input exceeds window - output_reserve - headroom. It is the default behavior.
  • Manual /compact forces compaction.
  • Manual /new-context appends a window.
  • Automatic window is the fallback when compaction cannot reduce enough: the latest turn alone is oversized, the summary call fails repeatedly, or the retained tail is still over budget. The fallback starts at the latest user turn and uses a static handoff note.

Failure and crash

  • The summary is a separate model call with no tools. Its usage, model, and provider are recorded on the compaction event.
  • If the summary call fails, append an attempt fact and do not append a compaction. The conversation is unchanged. Report the failure.
  • If the process crashes after the summary but before the compaction append, the log has no compaction. The next run retries.
  • If the compaction event is appended, it is committed. Recovery projects the summary and the retained tail.
  • An open tool call at the head blocks compaction until its result is recorded or the run is finalized with an interrupted result.

What not to store

Do not store the projected message list, the rendered system prompt per request, or a "replacement surface". Store the summary, the cut point, and the usage. That is enough to re-derive the conversation.

Acceptance criteria

  1. A real task on a real repository completes with the six tools through Codex.

  5. A long synthetic session compacts automatically; the projection after compaction contains the summary and the retained tail; the shadowed facts remain in the log.

9. Simplicity rules

There is no line budget. These rules are the review standard:

  • One source of truth. A fact has one home. If it can be derived, do not store it. If it is stored, do not keep a second copy.
  • One writer. Each mutable state has one owner and one write path. The log is the only durable conversation writer. Projection and request builders never write.
  • One-way flow. Log to projection to request to effects. A feature that adds a back-edge is rejected.
  • Pure at the center, I/O at the edges. Projection and request construction are pure. File, process, network, and model access live in tools, providers, and hosts.
  • One vocabulary. The loop emits the event types that the log stores. Hosts render them. No translation layer between two event models.
  • No speculative abstraction. An interface exists because a current caller needs it. Delete unused layers.
  • Deletion removes code. Removing a feature removes its branches, flags, and tests. A flag that keeps a dead path is a design failure.
  • Change face equals review face. A change carries only the lines its behavior needs. A migration moves code; it does not rewrite it.

Review questions for each change:

  1. What fact or state does this add? Where is it stored?
  2. Who writes it? Is there a second writer?
  3. Can it be derived from the log? If yes, why store it?
  4. Does this function have side effects? Are they at the edge?
  5. Does this add a new mutable state owner or a new conversation event type?
  6. If this feature is deleted, what remains? If the answer is "flags and branches", the boundary is wrong.

A change that adds a new mutable state owner or a second conversation event type needs a design review, not a patch.

11. Decisions

  1. Package boundary. New src/cade/mini/ with an import firewall. It may import the standard library, cade.ai (provider adapters, auth, model registry), and cade.harness.execution_env (filesystem and shell primitives). It may not import cade.agent, cade.coding_agent, or any other cade.harness package. The current Cade stays runnable until Mini reaches parity.
  2. First provider. Codex/Responses, reusing the existing adapter and auth behind Mini's Provider protocol. Chat-completions can ship alongside it if the adapter is cheap; it is not a prerequisite.
  3. Compaction. Pi-style summary plus first_kept_id, stored as a compaction event. Default automatic compaction. Explicit window plus automatic fallback. Never store the projected replacement.
  4. Session format. A new format, versioned from day one. No compatibility layer with current Cade sessions. Import only if a real need appears.
  5. Host. CLI plus REPL first. TUI and web are later hosts on the same event stream.
  6. Entry point. cade-mini during development. Switch cade only after the acceptance criteria pass on a real workflow.
  7. Process. The first task is the harvest audit and the schema decision record. Every structural decision gets a short record with problem, decision, alternatives, and consequences.

  • Storing derived projections, rendered history, or replacement message lists.
  • Automatic model fallback.
  • LLM-based permission decisions in the first increment.
  • A plugin runtime in the first increment.
  • Backward compatibility with Cade's current session format.
  • Feature parity before the pipeline is proven. Parity is the goal; the order is the plan.

Snapshot undo

What it is: before and after each user turn, Cade writes a Git tree of the workspace into a hidden repository under .cade/snapshots/<session>/.git. It stores the changed-file list in an index. /undo checks each file for conflicts, restores the pre-turn content, and reports per-file results.

Why defer: it is a host/product safety feature, not pipeline. It adds per-turn Git work, an index, conflict semantics, and write permissions. Git already gives the user git diff, git checkout, and git stash.

If wanted later: harness/snapshot.py is self-contained (451 lines, no cade imports) and can be ported almost verbatim. The first increment can record a workspace fingerprint or print git status at turn end.

Recommendation: defer. Revisit after the first increment if Git is not enough.

The first workflow ran Mini with --mode build --yes. Cade ran with --mode build --approval auto-review; its automatic reviewer approved the pytest command. The second workflow used the same settings.

Observations

  • Both agents read before editing, changed only the necessary files, ran pytest, and reported the verified result.
  • Both produced the same source changes for the bug fix and the feature.
  • Both resumed their prior session and recalled the earlier bug.
  • Cade emits a JSONL event stream and additional budget/approval telemetry; Mini emits human-readable tool progress and records request/run facts in its session log.
  • Mini used one more model step because it also issued a glob inspection. This did not change the result.

  • Mini has no OS sandbox; it relies on path boundaries, modes, shell classification, and approvals.
