Cade Mini

Cade Mini is a standalone coding agent. It keeps one rule at the center of the design:

The session log is the source of truth. The model-visible history is a deterministic projection. Request construction only produces the current request.

The result is a small agent that can survive compaction, window changes, and process restarts without inventing history.

Quickstart

Cade Mini requires Python 3.12 or newer. The repository uses uv for development and for the cade-mini entry point.

Install and authenticate

From the repository root:

uv sync --locked

Cade Mini owns its credential store at ~/.cade-mini/auth.json. Log in to Codex with a browser or device code:

uv run --locked cade-mini login
uv run --locked cade-mini login --method device_code

For an API-key provider, use a hidden key prompt or set its environment variable:

uv run --locked cade-mini login --provider deepseek
export DEEPSEEK_API_KEY=...
uv run --locked cade-mini --provider deepseek --model deepseek-flash "Review this project."

The default provider is openai-codex. Set provider and model in cade-mini.json to choose other startup defaults. Mini does not read Cade's credentials, skills, or settings.

Run one task

uv run --locked cade-mini "Read README.md and explain the entry point in three bullets."

The same command can be written explicitly:

uv run --locked cade-mini exec "Read README.md and explain the entry point."

Cade Mini runs in the current directory by default. Use --project-root to point at another workspace.

Choose a mode

  • act is the default. Reads run directly; writes and shell commands ask.
  • build allows structured writes and read-only shell commands. Mutating shell commands still ask.
  • plan hides write and edit tools and denies mutations. Read-only shell commands are allowed.
uv run --locked cade-mini --mode plan "Propose a fix for the failing test."
uv run --locked cade-mini --mode build "Fix the bug and run the test."

For non-interactive automation, --yes approves asks, and --read-only denies writes and shell commands. Prefer rule-based allows over --yes for shared repositories; see Configuration.

Continue work

Sessions live under .cade-mini/sessions by default.

uv run --locked cade-mini --list-sessions
uv run --locked cade-mini --continue "What did you change?"
uv run --locked cade-mini --resume SESSION_ID "Continue the task."

Omitting the task starts the interactive REPL. See CLI for all REPL commands.

Open the web host

uv run --locked cade-mini --web --port 8765

Open http://127.0.0.1:8765. The web host has no terminal prompt, so writes and shell commands are denied unless you start it with --yes or use rules. The host serves one durable session for its lifetime.

Build the docs

uv sync --locked --extra docs
uv run --locked python -m cade_mini.docs check
uv run --locked python -m cade_mini.docs build

Open docs/index.html. The docs source is under docs/cade-mini/.

CLI

The cade-mini entry point runs one task, starts a REPL, manages sessions, or serves the web host.

cade-mini [TASK] [options]
cade-mini exec TASK [options]

exec is an explicit alias for a one-shot task. Without a task, cade-mini starts the interactive REPL.

Login

cade-mini login
cade-mini login --method device_code
cade-mini login --provider deepseek

--provider defaults to openai-codex. Codex supports browser (default) and device_code; other providers use api_key with a hidden input prompt. Credentials are stored in ~/.cade-mini/auth.json. Login does not change project provider or model settings.

One-shot options

  • --project-root PATH sets the workspace. The default is the current directory.
  • --config PATH selects a config file. The default is <project-root>/cade-mini.json.
  • --provider NAME, --model NAME, and --effort EFFORT override provider defaults.
  • --mode plan|build|act selects the execution mode.
  • --read-only / --no-read-only denies or permits writes and shell commands.
  • --yes approves asks. Use it only in trusted, non-interactive contexts.
  • --auto-review / --no-auto-review lets the model review ask-level calls.
  • --max-steps N bounds model steps.
  • --context-window N overrides the model context window.
  • --json emits JSONL events for a one-shot task.
  • --steer TEXT injects guidance at the next model step; repeatable.
  • --queue TEXT queues a REPL task to run after the current task; repeatable.

Sessions

  • --list-sessions prints ID, update time, and title, then exits.
  • --continue resumes the latest session in the project.
  • --resume resumes the latest session; --resume ID resumes a specific one.
  • --sessions-dir PATH changes the session directory. A relative path is resolved against the project root.
  • --undo restores the latest file snapshot and exits without contacting a provider.

--continue and --resume cannot be combined.

Goals and web host

  • --goal TEXT sets the workspace goal before running.
  • --web starts the local web host instead of the REPL.
  • --host and --port bind the web host. The default is 127.0.0.1:8765.

REPL commands

  • /new starts a new session.
  • /resume [ID] resumes the latest or a specific session.
  • /sessions lists project sessions.
  • /fork [N|ENTRY] forks before a recent user turn or entry. N=1 is the latest.
  • /clone copies the current branch to a new session.
  • /tree shows entries; * marks the active branch.
  • /rewind [N] creates a session without the latest N user turns.
  • /compact summarizes older turns.
  • /new-context [NOTE] starts a new window, optionally with a handoff note.
  • /mode [MODE] shows or switches the execution mode.
  • /permissions [clear] shows or clears session grants.
  • /undo [N] restores the latest N snapshots.
  • /goal [TEXT|done|clear] shows, sets, completes, or clears the goal.
  • /context prints the session ID, provider, budget, and event count.
  • /steer TEXT queues guidance for the next model step.
  • /queue TEXT queues a task to run after the current one.
  • /stop cancels the current task at the next safe point.
  • /help prints the command list.
  • /exit or /quit exits.

REPL input

  • @path attaches a workspace file to the task.
  • $skill loads a skill body into the task.
  • !command runs a shell command without contacting the model. Permission checks still apply.
Review @src/cade_mini/core/loop.py and use $review-only
!git status

During a task, the REPL keeps reading input:

  • /steer TEXT appends guidance at the next model step.
  • /queue TEXT runs TEXT after the current task.
  • /stop cancels at the next safe point.
  • Other text is queued as a follow-up task.

Steering is applied between steps, not inside a provider stream or a running tool. See Steering and queueing.

Exit codes

  • 0: the run completed.
  • 1: the run ended without completion, or no snapshot was available for --undo.
  • 2: argument, configuration, or startup error.
  • 130: login was cancelled.

Configuration

Cade Mini reads <project-root>/cade-mini.json by default. Use --config PATH to select another file. Command-line options override the file; the file overrides built-in defaults.

The file is strict: unknown keys and invalid values are rejected instead of silently ignored.

Example

{
  "provider": "deepseek",
  "model": "deepseek-chat",
  "reasoning_effort": "high",
  "context_window": 128000,
  "max_steps": 30,
  "sessions_dir": ".cade-mini/sessions",
  "mode": "act",
  "read_only": false,
  "instructions": true,
  "note": true,
  "memory": true,
  "auto_review": false,
  "prompt_modules": ["identity", "tool_discipline", "working_note", "environment"],
  "rules": [
    {
      "tool": "bash",
      "command_prefix": "git status",
      "decision": "allow"
    }
  ]
}

Fields

  • provider, model: provider name and model identifier. The CLI flags override both.
  • reasoning_effort: provider reasoning effort. The CLI flag is --effort.
  • context_window: model context window in tokens.
  • max_steps: maximum model steps in one run.
  • sessions_dir: session directory. Relative paths resolve against the project root.
  • mode: plan, build, or act.
  • read_only: deny writes and shell commands.
  • instructions: load AGENTS.md or CLAUDE.md into request context.
  • note: load NOTE.md working state.
  • memory: load MEMORY.md durable facts.
  • auto_review: let the model review ask-level tool calls. Default is false.
  • prompt_modules: system prompt modules. Available names are identity, tool_discipline, working_note, and environment.

Rules

Rules are evaluated last match first. A rule matches a tool name or *, and optionally a path or command prefix. decision is allow, deny, or ask.

{
  "rules": [
    {"tool": "bash", "command_prefix": "git", "decision": "deny"},
    {"tool": "bash", "command_prefix": "git status", "decision": "allow"},
    {"tool": "write", "path_prefix": "docs/", "decision": "allow"}
  ]
}

Hard boundaries win over rules: a path outside the workspace is denied even if a rule allows the tool. read_only also wins over grants and rules.

Hooks

Hooks run shell commands around tools. A non-zero before_tool hook denies the call.

{
  "hooks": [
    {
      "event": "before_tool",
      "command": "python tools/check_tool.py",
      "matcher": "bash",
      "timeout_ms": 10000
    }
  ]
}

event is before_tool or after_tool. matcher is a tool name, a prefix ending in *, or omitted for all tools. Hooks receive CADE_HOOK_EVENT, CADE_TOOL_NAME, CADE_TOOL_ARGS, and CADE_TOOL_RESULT in the environment.

MCP servers

MCP servers use stdio and keep one persistent connection per server.

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["mcp_server.py"],
      "cwd": ".",
      "timeout_ms": 30000,
      "env": {"LOG_LEVEL": "warn"}
    }
  }
}

Discovered tools are exposed as mcp__<server>__<tool>. They ask by default, are denied in plan mode and read-only mode, and can be allowed by a rule.

Architecture

Cade Mini is a pipeline with four stages. Each stage has one owner and one direction of data flow.

Session log -> Conversation projection -> Request -> Run

Session log

SessionLog is an append-only JSONL file. Each entry has an ID, timestamp, type, parent ID, and data. The active branch ends at the latest entry. A tree is possible, but the loop follows one branch.

The log stores facts:

  • system, user, assistant, and tool_result are model-visible facts.
  • compaction records a summary and first_kept_id.
  • window records a new context start and an optional handoff.
  • request, run, and attempt are audit facts. They never become conversation messages.

The schema is closed and versioned. See Session log schema.

Projection

project(entries) is a pure function. It reads the branch and produces the deterministic conversation projection:

  1. Take the latest system message.
  2. Apply the latest window start.
  3. Apply the latest compaction summary.
  4. Keep retained user, assistant, and tool-result messages.
  5. Pair tool calls with tool results; insert a synthetic interrupted result at the tail when the log ends mid-call.

No projection step writes to the log. Replaying the same entries always produces the same conversation.

Request

build(conversation, tools, budget, context) admits messages into the current model window. It:

  • joins request-only context such as instructions, skill catalog, NOTE, memory, and goal;
  • replaces old tool bodies with references to the history tool;
  • drops the oldest turns when needed;
  • converts the result to provider wire format;
  • returns a Request with a BuildReport.

Admission does not mutate the conversation and does not write facts. A request that still exceeds the budget is rejected rather than silently truncated.

Run

run() appends the user fact, calls the provider, appends assistant and tool-result facts, and executes tools. It is the only stage that writes during a turn. Compaction and window fallback are decisions expressed as new log facts.

Why the split

The split prevents a common failure: the request builder starts hiding messages, then the history rewrite becomes the only copy of what happened. Mini keeps the original facts and lets the projection and admission be replaced without losing history.

Sessions and context

A session is an append-only JSONL file under .cade-mini/sessions by default. The file name is session-<id>.jsonl. The session title is derived from the first user message; no extra event type is needed.

Resume

cade-mini --list-sessions
cade-mini --continue "Continue where we stopped."
cade-mini --resume SESSION_ID "Explain the current state."

--continue and --resume open the latest or a specific session. Existing sessions keep their original system fact; a new cade-mini.json does not rewrite history. If a resumed session has no system entry, the current prompt is added.

Fork, clone, tree, and rewind

  • /clone copies the active branch into a new session.
  • /fork [N|ENTRY] copies history before a user turn (default: latest) into a new session and prints the forked input.
  • /tree lists entries; * marks the active branch.
  • /rewind [N] creates a new session without the latest N user turns.
  • /undo [N] restores the latest N file snapshots.

These operations create new sessions; they do not rewrite the original file. Compaction and window references are remapped when entries are copied.

Compaction

When the full conversation exceeds the input budget, Compactor:

  1. Selects a cut at a visible user boundary.
  2. Sends the older messages to the provider for a summary.
  3. Appends a compaction fact with the summary and first_kept_id.
  4. Reprojects the conversation as the latest system, summary, and retained tail.

Compaction is iterative: a prior summary is serialized as PRIOR SUMMARY and can be summarized again. The original user, assistant, and tool-result facts remain in the log.

Pruning

Request admission replaces old tool results with a reference:

[tool output omitted; call_id=...; use the history tool ...]

The latest four tool results are protected first. If the request still does not fit, older protected results and finally the newest result can be replaced. The model can recover exact content with the history tool using call_id or entry_id.

Windows

A window fact starts a new context at a user entry and may include a handoff. The CLI can start one explicitly with /new-context. If compaction cannot bring a request under budget, the loop can append an automatic window with a fixed handoff that points to NOTE.md and the history tool.

History tool

history accepts one of:

  • query: case-insensitive search over the branch, returning entry IDs and snippets.
  • entry_id: exact content of one log entry.
  • call_id: exact tool result for one call.

Exact content is capped. Search results are capped and point back to entry IDs.

Request context order

For each task the request contains:

  1. The system message.
  2. Project instructions from AGENTS.md, CLAUDE.md, or their variants.
  3. The skill catalog.
  4. NOTE.md working state.
  5. MEMORY.md durable facts.
  6. An active goal.

Items 2-6 are request-only context. They are recorded in the request audit but never become conversation facts. See Architecture and the design.

How Cade Mini works

Cade Mini coordinates one model request at a time, executes the requested tools, and records every durable fact in a session log.

One run

A submitted task is appended as a user fact. Cade Mini projects the active branch, builds a request for the current budget, and sends it to the provider. The provider streams text and tool calls. The loop records the assistant message, executes each tool call, and records a tool result. If the model needs another request, the loop starts another step; otherwise the run ends.

A step is one request plus the tools caused by its response. A run can contain many steps. The loop stops on completion, a step limit, context exhaustion, cancellation, or a provider error.

Context

The projection supplies conversation history. Request-only context supplies project instructions, the skill catalog, NOTE.md, MEMORY.md, and an active goal. Tool results are pruned when they no longer fit; the history tool can read the original facts.

Compaction adds a summary fact and keeps a recent tail. A window moves the context start forward and may include a handoff. Neither operation rewrites the original messages.

Sessions

Sessions are JSONL files under .cade-mini/sessions. Entries have IDs and parent IDs, so a session can form a tree; the active branch ends at the latest entry. Resuming opens the same file and appends new facts.

Interfaces

The terminal host runs one task or a REPL. The web host serves a page and a small JSON API. Both call the same loop and share policy, tools, and session storage.

Extensions

Skills add on-demand instructions. Memory adds durable facts. Hooks run shell commands around tools. MCP adds remote tools. Subagents run an independent child session. Each extension is a narrow adapter over the loop, not a change to the session schema.

Trust and permissions

Every tool call passes through a policy. Modes, static rules, session grants, shell classification, and approvals decide whether a call runs. Cade Mini has no OS sandbox; the path boundary, mode, shell classification, and approvals are the active safety layer.

See Architecture for the invariant and Capability seams for the contracts.

Relationship to Cade

Cade and Cade Mini are separate projects. This repository develops, tests, and releases only Cade Mini. It does not provide compatibility with Cade's Python package, commands, settings, credentials, or session formats.

Mini originated as a log-first implementation alongside Cade. Its provider adapters and process execution code were brought into the cade_mini package when it became independent. They are no longer shared runtime dependencies.

Mini's product boundary

Mini provides a terminal REPL, one-shot execution, and a local web host. Its core separates append-only session facts, deterministic projection, request admission, and the run loop.

Intentional limits include:

  • No full-screen TUI, plugin runtime, RPC, or SDK.
  • No artifact store or parallel tool scheduler.
  • No permanent approval grants; durable rules belong in project config.
  • No OS sandbox; permissions and shell classification are application checks.

The historical parity acceptance records workflows tested before separation. It is not a promise of future feature parity. See the code map for the current package and ownership boundaries.

Capability seams

Cade Mini keeps a small number of explicit contracts. A seam is a place where an implementation can be replaced without changing the session schema or the loop.

Host A task runner over the loop CLI, web host Users

Provider

The loop needs a streaming event source: text deltas, tool calls, a final message, usage, and failures. A provider owns wire conversion and replay state. Cade Mini does not depend on provider-specific message types above this seam.

Tool

A tool declares a JSON schema and an async execute. A tool result is content, an error flag, and optional metadata. Tools do not write the session log; the loop records their results.

Policy and approval

Policy returns a decision, not an execution. Approval is only consulted for ask. A denial becomes a tool error fact, so the model can recover. Keeping these separate lets the host choose a TTY prompt, a model reviewer, or a non-interactive denial.

Hooks

Hooks observe and can veto a tool call without changing the policy result. A before_tool failure is a denial; after_tool failure is ignored. Hooks are trusted configuration, not sandboxed code.

Stores

SessionLog is the durable history. SnapshotStore, GoalStore, and the memory and NOTE files are host state, not session facts. Treating them as separate stores keeps the schema closed while allowing recovery and long-term state.

Host

A host owns presentation, input, and the event loop boundary. It does not own the agent loop or the schema. The CLI and web host differ only in how they run a task and render events.

Tests as contracts

Each seam has a focused test module. test_mini_boundary.py enforces the import firewall, so a seam cannot quietly become a dependency on the Cade product layers.

Event model

A session is a tree of entries, not a message array. Entry types fall into two groups.

Model-visible facts

These entries project into the conversation:

Type Meaning
system Base system prompt; the latest one wins
user User task or steering input
assistant Text and tool calls produced by one model response
tool_result Result paired to a tool call
compaction Summary plus first_kept_id; shadows older entries
window New context start plus optional handoff

compaction and window also carry projections of their own: a summary message. The original entries remain readable by the history tool.

Audit facts

These entries never project:

Type Meaning
meta Session creation metadata
request Provider, model, context, digests, estimated tokens, dropped evidence
attempt One provider attempt, including failures and retries
run Termination, steps, usage, error

Audit facts make the request reproducible without turning diagnostics into conversation. A failed run therefore cannot fabricate an assistant message.

Flow

flowchart LR
  log[Session log] --> project[Projection]
  project --> conversation[Conversation]
  conversation --> request[Request build]
  request --> provider[Provider stream]
  provider --> facts[Assistant and tool-result facts]
  facts --> log
  request --> audit[request fact]
  provider --> attempts[attempt facts]
  facts --> run[run fact]

The loop appends the user fact before the first request. Each step appends one assistant fact and zero or more tool-result facts. A run appends exactly one run fact.

Ordering and pairing

A tool result follows its assistant tool call. Projection rejects an orphan result or a duplicate result. If the branch ends after a tool call without a result, projection inserts a synthetic interrupted result at the tail so the request remains protocol-valid.

Compaction and windows

A compaction cuts at a user boundary. Its summary message appears first in the retained context. A window discards earlier entries and may insert a handoff. Only the latest cut applies. Compaction is preferred; a window is a fallback when a summary cannot fit.

Schema authority

The closed schema is in Session log schema. The generated event catalog lists the current event types from code.

Tool execution

Every tool call follows the same pipeline. Policy and approval decide whether a call may run; hooks can stop it; the loop owns execution and recording.

  call[Tool call] --> policy[Policy decision]
  policy -->|deny| denied[Denied tool result]
  policy -->|ask| approval[Approval]
  approval -->|deny| denied
  approval -->|allow| before[before_tool hooks]
  policy -->|allow| before
  before -->|deny| hookdenied[Hook-denied result]
  before -->|allow| execute[Execute tool]

  denied --> log
  hookdenied --> log

Order

  1. The model returns a tool call with an ID and arguments.
  2. Policy checks tool name, path, mode, rules, grants, and shell classification.
  3. An ask decision is resolved by the host: TTY prompt, --yes, auto-review, or denial.
  4. before_tool hooks run. A non-zero exit denies the call.
  5. The tool executes with a timeout and cancellation token.
  6. The result is truncated, appended as a tool_result fact, and rendered.
  7. after_tool hooks run and their output is ignored.

Denials and errors

A denied call is not an exception. It becomes an error tool result so the model can adapt. Unknown tools, malformed arguments, timeouts, and thrown exceptions also become error results. A cancellation appends interrupted results for any remaining calls before the run terminates.

Hooks

Hooks receive the tool name, JSON arguments, and the result for after_tool. They run with the workspace as the current directory. A hook timeout is a denial or a silently ignored observer, never an unbounded wait.

Evidence retention

Tool results are facts. Request admission can replace old bodies with a reference that names the call_id. The history tool retrieves the exact result from the branch, so pruning does not destroy evidence.

Steering and queueing

Cade Mini's REPL can read input while a task is running. The host does not block the terminal on _run_task.

Why the old REPL blocked

The first REPL called input() in the main thread and then ran the async loop with asyncio.run. While that call was active, the terminal was not read, so /steer and /queue could only affect the next task.

Current design

stdin
  |
  v
_InputPump thread  -- _Line -->  event queue
                                  |
task thread  -- _ApprovalRequest / _TaskDone --> event queue
                                  |
                                  v
                         REPL main thread
  • _InputPump reads one line at a time and never calls the model.
  • _run_task runs in a worker thread with its own asyncio event loop.
  • The REPL main thread owns the event queue and the session state.
  • _HostApprover sends _ApprovalRequest to the main thread and waits. The main thread reads the answer from the same input pump, so approvals do not compete with a second input().
  • !command runs in the main thread and uses _ConsoleApprover, which reads the answer directly from the event queue.

Commands during a run

Input Effect
/steer TEXT Append guidance at the next model step
/queue TEXT Run TEXT as a new task after the current task
/stop or /cancel Cancel the current task at the next safe point
other text Same as /queue: run it after the current task
/exit Cancel, wait for the task to settle, then exit

/steer is not a prompt injection into a running provider request. The loop checks the steering queue before each step, appends a user fact with source: runtime, and builds the next request from the projection. This keeps the session log as the source of truth.

Queue semantics

  • A queued task starts automatically when the current task reaches a terminal state.
  • Queue order is FIFO.
  • A queued task runs in the same session; it is not a fork.
  • /fork, /clone, /rewind, and session commands are main-thread commands. They are only handled when no task is active. During a run they are treated as queued text; finish or stop the run first.

Limits

  • Tools already executing are not killed. /stop takes effect at the next cancellation check.
  • The input pump uses plain input(), not a full line editor. Editing, history, and completion are terminal features.
  • Approval answers are read as the next line. Do not type a task while an approval prompt is waiting; it is consumed as the answer.
  • The one-shot --steer flag seeds guidance before the first step. It is not a substitute for /steer during a run.

The session log

The log is append-only and versioned. It stores model-visible facts and audit facts in one tree. It is the only artifact needed to reconstruct the conversation. Compaction and windows are log entries, not rewrites.

Snapshots

Snapshots are an undo journal for file changes. They cover write, edit, and common single-command shell mutations. The index is JSONL and each snapshot has a metadata file plus an optional payload. They are not part of the session branch.

Goals and notes

A goal is one objective with an active or done status. NOTE.md is working state that is included in every request and summarized during compaction. MEMORY.md is durable project knowledge. These files are intentionally plain: they can be edited by hand and inspected with ordinary tools.

Generated artifacts

The docs site, llms.txt, and llms-full.txt are generated from Markdown and docs.json. They are checked for freshness; do not edit the HTML by hand.

What is not persisted

  • Request-only context is recorded in the request audit, not as messages.
  • Grants last for the process; durable policy belongs in config rules.
  • Approval prompts and TUI state are host state.
  • Provider replay payloads live inside the assistant fact that produced them.

Glossary

One canonical term per concept. Links point to the owning page.

session log

The append-only JSONL file that records facts. It is the source of truth for the active branch. See Log.

branch

A path through the entry tree. The active branch ends at the latest entry and supplies the projection.

projection

The deterministic conversation produced from a branch. It applies the latest system, compaction, and window cuts, then pairs tool calls with results. See Projection and request.

request

The admitted, provider-ready form of a conversation for one model call. It includes tools, budget, and request-only context. A request is not a fact and is never projected.

run

One invocation of the loop over a task. A run contains one or more steps and ends with a run fact.

step

One model request plus the tool calls caused by its response.

tool result

The recorded output of one tool call, paired by call ID. It is a fact.

compaction

A fact that adds a summary and a first_kept_id. It shadows older messages in later projections without deleting them.

window

A fact that moves the context start forward, optionally with a handoff. It is a fallback when compaction cannot fit.

history

The tool that retrieves exact evidence by entry ID or call ID after compaction or pruning.

mode

plan, build, or act. A mode selects the default policy for tools and shell commands.

rule

A static policy entry in config. Rules can match tool, path prefix, and command prefix and return allow, deny, or ask.

grant

A process-local approval created by answering a. It matches the same tool and path or command.

hook

A configured shell command around a tool call (before_tool or after_tool).

skill

A SKILL.md body loaded on demand. The request carries a catalog; the skill tool loads the body.

MCP

Model Context Protocol. Cade Mini runs stdio MCP servers and exposes their tools as mcp__<server>__<tool>.

subagent

A child run with its own session and a restricted tool set. It cannot spawn another subagent.

snapshot

A pre-change copy of a file, used by --undo and /undo.

goal

A durable objective in .cade-mini/goal.json, separate from the session schema.

Log

SessionLog owns the append-only JSONL file.

Create and open

  • SessionLog.create(directory, session_id=None) creates a unique file and writes a meta entry.
  • SessionLog.open(path) validates the file and repairs a torn final line by appending a newline or dropping the incomplete tail.
  • The session ID is derived from the file name when not supplied.

Append

append(type, data):

  1. Takes an exclusive file lock.
  2. Reads the current tail to get the parent ID.
  3. Builds an entry with ID, timestamp, parent, type, and data.
  4. Appends one JSON line and flushes.
  5. Releases the lock.

fsync is deliberate: a returned append is durable enough to resume. A failed write raises LogError and does not return a fake entry.

Branch

branch() follows parent IDs from the last entry back to the root and reverses the list. It rejects cycles, missing parents, and duplicate IDs.

Listing and titles

list_sessions(directory) returns session ID, update time, and a title derived from the first user text. Corrupt files are skipped so one bad session cannot break the list.

Invariants

  • Entries are never rewritten in place.
  • IDs are unique within a file.
  • A parent precedes its child.
  • The file ends with exactly one newline.
  • The schema version is closed; new event types require a decision record.

Projection and request

Projection

project(entries) is pure. It:

  1. Finds the latest system entry.
  2. Applies the latest window start.
  3. Applies the latest compaction cut and emits a summary message.
  4. Converts user, assistant, and tool-result facts to messages.
  5. Pairs each tool call with its result by call ID.
  6. Inserts a synthetic interrupted result if the branch ends inside a call.

It rejects orphan results, duplicate results, and cuts that do not point to a user entry. The projection does not call a provider or write the log.

Request

build(conversation, tools, budget, context):

  1. Joins the base system prompt with request-only context.
  2. Estimates tokens.
  3. Replaces old tool bodies with references, keeping recent results first.
  4. Drops the oldest user turns if still over budget.
  5. Converts to provider messages and tool definitions.
  6. Returns a Request and a BuildReport.

BuildReport records estimated tokens, budget, dropped call IDs, and dropped turns. A request that cannot fit raises RequestTooLarge.

Pruning rules

  • The latest four tool results are protected in the first pass.
  • If still over, protected results are pruned oldest first.
  • The newest result is pruned only as a last resort.
  • The replacement names the call ID and points to the history tool.

Context order

The system message carries base instructions plus, in order: instructions, skill catalog, NOTE, memory, and goal. These inputs are request-only; the request audit records their digests and lengths, not their full text.

Tests

test_mini_projection.py, test_mini_request.py, and test_mini_compaction.py cover the cut, pruning, and wire-format contracts.

Loop

run(log, text, ...) is the only stage that writes during a turn.

One run

  1. Append the user fact.
  2. For each step:
    • Project the branch.
    • If the full estimate exceeds budget, call the compactor.
    • Build the request.
    • If still over, call the window fallback.
    • Append a request audit fact.
    • Stream the provider.
    • Append the assistant fact.
    • Resolve and execute each tool call.
    • Append tool-result facts.
  3. Append one run fact with termination, steps, usage, and error.

Provider handling

The loop collects text deltas, tool calls, usage, and provider replay state. A failure becomes an attempt fact. Retryable failures are retried once by default; the retry delay is configurable. A terminal failure ends the run with provider_error and never creates an assistant fact.

Termination

  • completed: the provider ended without tool calls.
  • step_limit: the configured step count was reached.
  • context_error: no request fits after compaction and window fallback.
  • aborted: cancellation was requested.
  • provider_error: the provider failed.

Cancellation

A cancellation token is checked between steps and tool calls. Running tools get the token; remaining calls receive interrupted results. The run records the reason in its run fact.

Events

The host receives text deltas, tool start, tool end, and final output. Events are presentation; facts are durable. A host can drop events without losing history.

Tests

test_mini_loop.py covers completion, tool use, approvals, retries, timeouts, cancellation, context errors, and window fallback.

Tools and policy

Tool contract

A tool has a name, description, JSON parameter schema, and async execute. Results carry content, an error flag, and optional metadata. The loop records results; a tool never appends to the log.

Built-in tools

  • Workspace: read, write, edit, glob, grep, bash.
  • Evidence and context: history, skill, memory, goal.
  • Delegation: subagent.
  • Remote: mcp__<server>__<tool>.

write and edit snapshot the target before changing it. bash snapshots common single-command mutation targets.

Policy

WorkspacePolicy.check returns allow, deny, or ask.

Hard checks run first:

  • read and file writes must stay inside the workspace.
  • bash workdir must stay inside the workspace.
  • Unknown tools are denied.
  • read_only denies writes, edits, shell, memory, and MCP.

Then:

  1. A matching static rule decides.
  2. A matching session grant allows.
  3. The mode default decides.

Modes:

  • plan: read tools and read-only shell; writes and mutations denied.
  • build: writes allowed; read-only shell allowed; mutating shell asks.
  • act: writes and shell ask.

Shell classification

classify_command labels a command read-only, mutating, or unknown. Pipelines, redirections, command lists, substitutions, and unknown binaries are unknown. Plan mode denies unknown; build asks; act asks.

Grants

GrantStore records a path or command for the exact tool. A grant is process-local. /permissions lists and clears it. Durable policy belongs in rules.

Approvals

The host resolves ask. SessionApprover prompts a TTY with yes/no/always. AutoReviewer makes one tool-free model call and requires an ALLOW prefix. Non-interactive hosts deny unless --yes or a rule allows.

Process isolation

There is no OS sandbox. Shell commands run with the Cade Mini process permissions. The path boundary, mode, shell classification, and approvals are the safety layer.

Context and compaction

Request context

The system message is the base prompt plus request-only context:

  1. Project instructions from AGENTS.md, CLAUDE.md, or variants.
  2. Skill catalog names and descriptions.
  3. NOTE.md working state.
  4. MEMORY.md durable facts.
  5. An active goal.

The request audit records this context's digests; it does not turn the text into conversation messages.

Compaction

Compactor runs when the full projection exceeds the input budget.

  1. Select the cut at a user boundary that keeps the recent tail under the configured target.
  2. Serialize older messages, including a prior summary.
  3. Ask the provider for a summary with a bounded output.
  4. Append a compaction fact with summary and first_kept_id.
  5. Reproject.

A summary failure or a cut with no messages appends an attempt fact and leaves the conversation unchanged. A prior summary is included as PRIOR SUMMARY, so compaction is iterative.

Window fallback

If compaction cannot fit, the loop may call the window hook. The CLI starts a window at the latest user entry with a fixed handoff that points to NOTE.md and history. If the request still does not fit, the run terminates with context_error.

History

The history tool searches the branch or reads an exact entry or tool result. It is the recovery path for evidence replaced during pruning or compaction. Exact content is capped; search results point to entry IDs.

Request pruning

Admission replaces old tool bodies with references before it drops turns. The history tool remains the only exact source. See Projection and request.

Tests

test_mini_compaction.py, test_mini_window.py, test_mini_history.py, and the request tests cover cuts, summaries, fallback, and retrieval.

Extensions

Extensions add behavior through narrow seams. None changes the session schema.

Skills

Discovery reads SKILL.md from user and project roots. The request carries a catalog; the skill tool loads a body into a tool result. A body is a fact, not request-only context.

Memory

MEMORY.md is request context. The memory tool appends one bullet and cannot write other paths. The file is capped to protect the request budget.

Hooks

HookRunner executes configured shell commands around tools. before_tool can deny; after_tool observes. Hooks are trusted and time-bounded. See Hooks, MCP, and subagents.

MCP

Each configured stdio server keeps one persistent process. Discovery reads tools/list; calls use tools/call over a serialized queue. Tools are prefixed mcp__, ask by default, and are denied in plan and read-only modes. A server that cannot start is reported and skipped.

Subagents

SubagentTool creates a child session under <sessions>/subagents. The child gets the parent provider, budget, policy, approver, hooks, context, and base tools plus its own history. It cannot spawn another subagent and is limited to 20 steps. The parent records only the call and summary. DelegateTool runs one or more child tasks sequentially and optionally applies a child mode.

Snapshots

SnapshotStore captures write, edit, and common single-command shell mutations. --undo and /undo restore the latest snapshot. Snapshots are project state, not session facts.

Goals

GoalStore persists one objective in .cade-mini/goal.json. The goal tool and /goal command manage it. An active goal is request context.

Hosts

The CLI runs one-shot and REPL sessions. The web host serves a page and a small JSON API over one session. Both use the same loop and policy.

Limits

Extensions are deliberately small. MCP is a stdio client, not a full capability negotiation implementation. Hooks are shell commands, not in-process callbacks. Subagents are sequential and share the parent approval context.

Tools and security

Workspace tools

  • read: read a UTF-8 file with line numbers. Files are capped.
  • write: write UTF-8 text and create parent directories.
  • edit: replace one exact occurrence of old text.
  • glob: list files matching a workspace glob.
  • grep: search file contents with a regular expression.
  • bash: run a shell command in the workspace.

Context and extension tools

  • history: retrieve compacted or pruned evidence.
  • skill: load the full body of an available SKILL.md.
  • memory: append a durable fact to MEMORY.md.
  • goal: read, set, complete, or clear the workspace goal.
  • subagent: run one child task in its own session.
  • delegate: run one or more child tasks sequentially, optionally in a mode.
  • mcp__<server>__<tool>: tools discovered from a configured MCP server.

Modes

plan exposes read, glob, grep, history, skill, and bash. Writes and edits are hidden and denied. Only classified read-only shell commands are allowed.

build exposes all tools. Writes and edits are allowed. Read-only shell commands are allowed; mutating or unknown commands ask.

act exposes all tools. Writes, edits, and shell commands ask.

--read-only denies writes, edits, shell commands, memory, and MCP regardless of mode. It does not block reads, search, history, skills, or goal state.

Rules and grants

Static rules live in cade-mini.json. They are evaluated last match first and can match tool, path prefix, and command prefix. A hard path boundary always wins.

A session grant is created when an approval answer is a (always). The grant matches the same tool and the same path or command. /permissions lists grants; /permissions clear removes them. Grants last for the process only. Use rules for durable policy.

Shell classification

The shell analyzer labels a command as read_only, mutating, or unknown. It is deliberately conservative:

  • ls, cat, grep, rg, git status, git diff, and similar commands are read-only.
  • rm, mv, cp, git commit, python, and other mutating commands are mutating.
  • Pipelines, redirections, command lists, substitutions, and unknown binaries are unknown.

Plan mode denies unknown commands. Build and act ask.

Approvals

An ask is answered by:

  • --yes: approve.
  • --auto-review: ask the model for ALLOW or DENY; failures deny.
  • Otherwise a TTY prompt: y once, n deny, a always for this exact call.
  • Non-TTY without --yes or auto-review: deny.

Process isolation

Cade Mini does not implement an OS sandbox. bash runs with the permissions of the Cade Mini process. The path boundary, modes, shell classification, and approvals are the safety layer; do not run untrusted commands or repositories with --yes.

Best practices

  • Use plan for review and build for scoped edits.
  • Prefer explicit rules over --yes in shared repositories.
  • Keep commands simple so the classifier can reason about them.
  • Use --read-only for inspection-only automation.

Snapshots and goals

File snapshots

Cade Mini records a snapshot before a file tool changes a file. Snapshots live under .cade-mini/snapshots with a JSONL index and one directory per snapshot.

Covered changes:

  • write and edit.
  • Common single-command shell mutations: rm, mv, cp, touch, mkdir, redirection with >, and sed -i.
  • Creating a file records that it did not exist; undo removes it.

Not covered:

  • Complex pipelines, command lists, unknown scripts, and commands that mutate files without naming them.
  • Files larger than the snapshot limit (5 MiB) are rejected rather than silently skipped.
  • Directory trees are not copied; directory mutations are skipped.

Undo

cade-mini --undo

This restores the latest snapshot and exits without contacting a provider. In the REPL, use /undo. Each call restores one snapshot, so repeated undo walks back through the recorded changes.

Snapshots are project state, not session facts. They are not part of the JSONL session branch.

Goals

A goal is one durable objective stored in .cade-mini/goal.json. It has an objective, a status (active or done), and an update time.

cade-mini --goal "Add a regression test for the parser" "Start the task."

In the REPL:

  • /goal shows the current goal.
  • /goal TEXT sets an active goal.
  • /goal done marks it complete.
  • /goal clear removes it.

The goal tool provides the same actions to the model. An active goal is added to request context so a resumed or compacted session still knows the objective. Goals are host state; they do not change the session schema.

Goals are intentionally small. Use NOTE.md for working details and MEMORY.md for facts that outlive the objective.

Skills and memory

Skills

Cade Mini discovers SKILL.md files in two roots:

  1. ~/.cade-mini/skills/<name>/SKILL.md for user skills.
  2. <project>/.cade-mini/skills/<name>/SKILL.md for project skills.

Later roots override earlier roots with the same skill name. A skill file can start with YAML frontmatter:

---
name: release-check
description: Validate release metadata before tagging.
---

Run the release checklist...

name defaults to the parent directory. description defaults to the first non-empty body line. Invalid names and empty bodies are skipped.

The request gets a compact <available-skills> catalog with names and descriptions. The model loads a body on demand with the skill tool:

{"name": "release-check"}

Skill bodies are facts in the tool result, not request-only context. Loading the same skill twice is harmless but adds another tool result.

Memory

MEMORY.md at the project root stores durable facts. It is loaded into request context as <memory source="MEMORY.md"> on every task, capped at 32 KiB.

The model appends facts with the memory tool:

{"text": "Prefer pytest and keep changes minimal."}

memory writes only MEMORY.md; it cannot write arbitrary paths. The file is capped at 64 KiB for writes. Remove stale entries manually when it fills.

Memory is different from the other state files:

  • AGENTS.md is project instruction, owned by the project.
  • NOTE.md is short-lived working state; it is summarized with compaction.
  • MEMORY.md is a durable preference or convention.
  • The session log is the record of what happened.

Request context

Instructions, skill catalog, NOTE.md, MEMORY.md, and an active goal are all request-only context. They appear in each request audit but never become conversation messages. See Sessions and context.

Hooks, MCP, and subagents

Hooks

Hooks run shell commands around tools. They are configured in cade-mini.json:

{
  "hooks": [
    {
      "event": "before_tool",
      "command": "python tools/check_tool.py",
      "matcher": "bash",
      "timeout_ms": 10000
    }
  ]
}
  • before_tool runs after policy and approval, before the tool executes. A non-zero exit denies the call and records an error tool result.
  • after_tool runs after a successful or failed executed tool. Its output is ignored.
  • matcher is an exact tool name, a prefix ending in *, or omitted for all.
  • Commands run with the workspace as the working directory and receive CADE_HOOK_EVENT, CADE_TOOL_NAME, CADE_TOOL_ARGS, and CADE_TOOL_RESULT.

Hooks are trusted configuration. A hook that hangs is killed after its timeout.

MCP

MCP servers use stdio. Cade Mini starts one persistent process per server and discovers its tools at startup:

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["mcp_server.py"],
      "timeout_ms": 30000
    }
  }
}

Tools are named mcp__<server>__<tool>. Their input schema comes from the server's tools/list response. Calls run sequentially over the connection and preserve server state.

Policy:

  • plan mode hides MCP tools and denies them.
  • read_only denies them.
  • build and act ask by default; a rule can allow a specific tool.

A server that fails to start is reported at startup and skipped. Connections are closed at process exit.

Subagents

The subagent tool runs one child task in its own session and returns the final answer with the child session ID:

{"prompt": "Find the failing test and report the file and line."}

The child:

  • gets the parent's provider, budget, policy, approver, hooks, and request context;
  • gets the base tools plus a history tool bound to its own log;
  • does not get another subagent tool, so it cannot recurse;
  • uses at most 20 steps;
  • writes its own session under <sessions>/subagents/.

The parent records only the tool call and the returned summary. The child log keeps the detailed evidence.

delegate uses the same runner for one or more tasks:

{"tasks": ["Inspect the parser", "Add a regression test"], "mode": "build"}

Tasks run sequentially in separate child sessions. Each result includes the child session ID; the parent gets one combined tool result.

Limits

MCP is a small stdio client, not a full capability negotiation implementation. Hooks are shell commands, not in-process callbacks. Subagents are sequential and share the parent's approval context rather than running in parallel.

Cookbook

Procedures with a concrete outcome and a verification step. Each recipe names the mode and the evidence to keep.

  • Fix a bug: reproduce, patch, verify, report.
  • Add a feature: test, implement, verify, review the diff.
  • Review only: investigate in plan mode without mutations.
  • Run a long session: NOTE, compaction, history, and goals.
  • Connect a custom MCP server: configure, allow, call, inspect.

For command details, see CLI and Configuration.

Fix a bug

Use build mode for the change. Keep the patch minimal and verify with the repository's tests.

Procedure

  1. Reproduce the failure:

    cade-mini --mode plan "Read the failing test and explain the failure."

  2. Fix it:

    cade-mini --mode build --yes "Fix the failing test with the smallest change, then run pytest."

  3. Inspect the diff and the snapshot:

    git diff
cade-mini --undo  # only if the change is wrong

Verify

  • The targeted test passes.
  • The full relevant test file passes.
  • The diff contains only the intended change.
  • The assistant names the command it ran.

Keep

The run log records the request, tool calls, and test output. The snapshot allows recovery before the next run. For a reviewable change, keep the diff in the commit, not in a docs file.

Avoid

  • --read-only when you intend to edit.
  • --yes on a shared repository without rules.
  • A broad refactor when a one-line condition fixes the test.

Add a feature

Write the test first, then implement, then verify. Use build mode and keep the diff reviewable.

Procedure

  1. Ask for a failing test or write it yourself:

    cade-mini --mode build --yes "Add a test for mul() that asserts 2 * 3 == 6; run it and confirm it fails."

  2. Implement the smallest change:

    cade-mini --mode build --yes "Implement mul() and run the new test."

  3. Review:

    git diff
pytest -q

Verify

  • The new test fails before the change and passes after it.
  • Existing tests still pass.
  • The implementation has no unrelated edits.
  • Public behavior is documented in the relevant guide.

Undo

If the change is wrong, use cade-mini --undo or /undo before starting another attempt. Undo restores one recorded file change at a time.

Keep

Update the guide or decision record when the feature changes a public contract. Tests belong in tests/; docs belong under docs/cade-mini/.

Review only

Use plan and --read-only when the task is to inspect, not change.

Procedure

cade-mini --mode plan --read-only "Review the request builder for evidence loss. Cite files and lines; do not modify anything."

Plan mode hides write and edit tools and denies mutating shell commands. --read-only also denies memory, MCP, and any remaining mutation.

Verify

  • git status is clean.
  • The answer cites files by relative path and line.
  • Claims about tests name the command and result.
  • Findings distinguish a bug from a preference.

Keep

For a review, keep the report in the conversation or a review document. Do not create a working note unless the review spans multiple sessions.

Limits

The model can still read anything inside the workspace. A review of untrusted code still needs human judgment; the policy prevents writes, not misleading prose.

Run a long session

Long tasks need durable state and a way to recover context. Use NOTE.md, a goal, and the history tool.

Procedure

  1. Set a goal:

    cade-mini --goal "Migrate the request builder to the new budget model" "Start by mapping the current admission rules."

  2. Keep a working note. Ask the model to update NOTE.md after each milestone:

    Update NOTE.md with completed work, current blockers, and the next action.

  3. Continue the same session:

    cade-mini --continue "Resume from NOTE.md and run the next step."

  4. Compact when the session grows:

    /compact

  5. Recover an old detail:

    Use history with query "budget" to find the earlier discussion.

Verify

  • NOTE.md names the next action, not just history.
  • A resumed run can continue without the original terminal.
  • The goal is marked done only when its acceptance check passes.

Limits

NOTE.md is request context and is summarized during compaction. MEMORY.md is for durable facts, not a task log. The session log is the authority for exact evidence.

Connect a custom MCP server

MCP servers use stdio. Cade Mini keeps one process per server and exposes each tool as mcp__<server>__<tool>.

Configure

Add the server to cade-mini.json:

{
  "mcp_servers": {
    "files": {
      "command": "python",
      "args": ["tools/mcp_files.py"],
      "timeout_ms": 30000,
      "env": {"LOG_LEVEL": "warn"}
    }
  }
}

command and args are required; cwd, env, and timeout_ms are optional. A relative cwd resolves against the project root.

Allow

MCP tools ask by default. Add a rule for a specific tool if unattended runs need it:

{
  "rules": [
    {"tool": "mcp__files__read_file", "decision": "allow"}
  ]
}

Plan mode and --read-only deny MCP tools even with a rule.

Verify

  1. Start Cade Mini; it prints a startup error if the server cannot start.
  2. Ask the model to list or call a discovered tool.
  3. Check the tool result and the mcp__ prefix in the log.
  4. Stop Cade Mini; the server process closes at exit.

Limits

The client implements initialize, tools/list, and tools/call. It does not implement resources, prompts, sampling, or server-initiated requests. A server that hangs is killed after the configured timeout.

Hosts

Cade Mini has two hosts: the terminal CLI and a local web host. Both use the same session log, request builder, tools, and policy.

Terminal

Without a task, the CLI starts a REPL:

cade-mini

The REPL prints tool progress to stderr, streams assistant text to stdout, and accepts the commands listed in CLI. With a task, it runs once and exits:

cade-mini "Fix the failing test."
cade-mini exec "Fix the failing test."

One-shot mode supports --json for a JSONL event stream. The REPL does not.

Web

cade-mini --web --host 127.0.0.1 --port 8765

Open http://127.0.0.1:8765. The page submits tasks and displays the final answer.

Endpoints:

  • GET / serves the page.
  • POST /api/task accepts {"task": "..."} and returns the answer, termination, steps, error, and session ID.
  • GET /api/sessions returns the session list.

The web host serves one session for its lifetime. Requests are serialized so two browser tabs cannot interleave turns.

Security:

  • The server binds to loopback by default.
  • There is no terminal to answer an approval prompt. Without --yes or a rule, writes and shell commands are denied while reads still work.
  • --read-only denies mutations explicitly.

Choosing a host

Use the terminal for interactive review and approvals. Use the web host for a small local console or a demo. Use one-shot mode for scripts and CI, with --read-only or explicit rules rather than a blanket --yes.

There is no separate TUI workbench. The REPL provides terminal interaction, and the web host provides a browser surface.

Template

0001: Compaction cut pointed at a shadowed user entry

Date: 2026-10-18

Status: resolved

Impact

After a prior compaction, the next compaction could choose a first_kept_id from a user entry that was already shadowed. The summary covered the wrong tail, and the retained window could omit the current task.

Timeline

  • The compactor collected all user entries from the branch.
  • It collected user positions from the visible projection.
  • It chose a cut by visible position but indexed the full branch entry list.
  • A session with a prior compaction therefore pointed at an older, shadowed user entry.

Root cause

Two lists with different lengths were treated as parallel arrays. A compaction removes old user entries from the projection but leaves them in the branch. The index into visible positions is not an index into all branch users.

Fix

The compactor now aligns with the last N user entries, where N is the number of visible user messages. A regression test builds a session with a prior summary, a retained turn, and a new task, then asserts the new cut points at the new task and the summary request contains the prior summary.

Verification

test_mini_compaction.py::test_iterative_compaction_includes_prior_summary passes. The projected roles are system, summary, user.

Follow-up

Any future cut logic must derive entry IDs from the same visible sequence it uses to choose positions. See Context and compaction.

0002: One huge tool result exhausted the request budget

Date: 2026-10-18

Status: resolved

Impact

A single tool result larger than the input budget could make a request impossible. The request builder protected the most recent four tool results, so a lone huge result was never replaced, and the run ended with context_error.

Timeline

  • A tool returned a result larger than the budget.
  • Admission protected the result because it was among the latest four.
  • Turn dropping removed old turns but not the current turn's huge result.
  • The request remained over budget and the run failed.

Root cause

The pruning policy treated "recent" as always protected. Protection is a heuristic for preserving working evidence, not a hard invariant. With only one result, the protected set was the entire candidate set.

Fix

Admission now prunes in passes:

  1. Replace unprotected results, oldest first.
  2. If still over, replace protected results oldest first.
  3. If still over, replace the newest result as a last resort.

Every replacement points to the history tool, so the evidence remains retrievable. A regression test covers a single huge result.

Verification

test_mini_request.py::test_build_prunes_a_single_huge_tool_result passes and the resulting request is under budget.

Follow-up

Keep the history tool available whenever pruning can remove the newest result. See Projection and request.

Persistence

Cade Mini has one durable conversation format: the session log. The rest are host-state files with narrow scopes.

Current format

  • Session log: schema v1, closed. See Session log schema.
  • Entry file: one JSON object per line; a trailing newline is required.
  • Session directory: .cade-mini/sessions.
  • Compaction and windows are entries, not file rewrites.
  • Snapshots, goals, NOTE, memory, and config are separate artifacts.

Compatibility

A reader must reject an unknown schema version rather than guess. A writer must not add fields that change the meaning of existing fields. Additive diagnostic fields are allowed only when old readers can ignore them.

History

There are no format migrations yet. When the first change lands, add a record under upgrade and a decision record describing the migration and rollback.

Verification

test_mini_log.py, test_mini_projection.py, and test_mini_acceptance.py exercise the current format. A schema change must add a test that opens an old fixture and one that rejects a future version.

Related

  • Persistence catalog
  • Change policy
  • Session log schema

Change policy

A persisted format change is a public interface change. It needs a decision, tests, and a migration path.

Before changing the schema

  1. Write a decision record under docs/cade-mini/decisions/.
  2. State whether the change is additive, transformative, or breaking.
  3. Describe how an old session is read and whether it is rewritten.
  4. Define the new schema version and the reader's rejection rule.
  5. Add an old-format fixture and a migration test.

Rules

  • Never rewrite a user's session file in place without an explicit migration.
  • Never infer a missing field from a provider's current behavior.
  • Keep audit facts out of the projection unless the schema says otherwise.
  • Bump the version for any change that an old reader cannot ignore.
  • Update Persistence, the schema, and the upgrade guide in the same change.

Review checklist

  • Old fixture opens and projects identically.
  • Unknown future version fails with a clear error.
  • Migration is idempotent and can be interrupted.
  • New fields have a documented owner and lifetime.
  • Session size and compaction behavior remain bounded.

Current status

Schema v1 is closed. No migration exists. The next format change must add the first entry to the upgrade guide.

Upgrade guide

This page records changes that require action from an existing user or automation.

Standalone project

Cade Mini now installs as cade-mini, with Python imports under cade_mini. The old cade command and cade.mini namespace are removed. No compatibility or migration tools are provided.

Authenticate again with cade-mini login. Credentials and skills use ~/.cade-mini/; project skills use .cade-mini/skills/. Mini no longer reads .cade directories. Session schema v1 remains the current format.

When an upgrade is needed

An upgrade entry is required when:

  • the session schema version changes;
  • a config key is renamed or removed;
  • a CLI flag changes meaning;
  • a tool name or parameter becomes incompatible;
  • a persisted host-state file changes shape.

Procedure for a future upgrade

  1. Read the relevant decision record.
  2. Back up .cade-mini/ before migrating.
  3. Run the documented migration command once.
  4. Open a session and verify the projection and history tool.
  5. Keep the old directory until the new version has passed a real task.

Compatibility promise

Additive optional config fields are not breaking. A new event type is breaking because the schema is closed. A removed tool or a changed parameter is breaking. The change policy is in Persistence.
